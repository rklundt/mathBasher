# Sprint 0.5.4: Click-to-start Splash + Button-Click SFX

**Phase:** Foundation
**Status:** Closed (2026-05-09)
**Released:** v0.5.4
**Blocks:** 0.5.5 Refactor pass
**Depends on:** 0.5.3 Audio + Settings
**Estimated effort:** 0.5–1 day

## Summary

Two coordinated UI-audio additions:

1. **Click-to-start splash** — defer `Phaser.Game` construction until the user clicks a splash overlay. Eliminates the `AudioContext was prevented from starting automatically` browser warning, properly brackets iOS Safari's first-gesture audio context creation, and gives a natural title-screen moment.
2. **Button-click SFX (`button-click-1.mp3`)** — wire the audio asset shipped during 0.5.3 (`public/assets/audio/sfx/button-click-1.mp3`) to every PlaceholderButton activation across the project. Plays through the existing AudioManager `play(key, 'sfx')` path, so it respects the SFX volume slider + master mute automatically. The splash's "Tap to play" button is the very first trigger.

Both pieces are small (~50 LOC for the splash, ~20 LOC for the wire-up) and additive — no service-layer changes. Phaser still constructs the same way, just deferred by one user click; PlaceholderButton's existing onClick now also pings the AudioManager.

## Stories

### Story 1: Splash overlay HTML + CSS

**Type:** Code
**Output:** `index.html` (add `<div id="splash">` + inline styles), `src/styles.css` if a separate stylesheet is preferred

**Acceptance:**
- A full-viewport overlay (`position: fixed; inset: 0; z-index: 10`) sits above the `<div id="game">` on page load
- Centered: project title (large, e.g. `<h1>mathBasher</h1>`) + a single button (`Tap to play` — touch + keyboard friendly wording)
- Background matches the in-game palette (deep slate `#0b1020`) so the transition feels continuous, not jarring
- Button is large enough for kid taps: minimum 44x44 device-independent px (Apple HIG min). 56x56+ recommended.
- CSS class `.hidden` (display: none) for the splash is defined and ready to apply on click
- No JS imports in the HTML — boot logic lives in `src/main.ts`
- Looks clean both in light + dark browsers (test against Firefox + Chrome default themes)

### Story 2: Defer Phaser construction until splash click

**Type:** Code
**Output:** Refactor `src/main.ts`

**Acceptance:**
- The top-level `new Phaser.Game(...)` call moves into a `startGame()` function
- A click handler on `#splash-start` (registered via `addEventListener('click', startGame, { once: true })`) calls `startGame()` once
- `startGame()` constructs `Phaser.Game` AND adds the `.hidden` class to `#splash` AND eagerly creates the AudioManager singleton (move from current top-level call)
- Page load no longer auto-starts the game; user MUST click the splash button
- Telemetry: log `SplashStarted` (info) at the click — gives us "did the user even click play" coverage in App Insights once it's wired
- The AppBoot Started/Completed telemetry events still fire at module load (those are about the tooling boot, not the game start) — verify they're not lost

### Story 3: Update BootScene title display

**Type:** Code
**Output:** `src/game/scenes/BootScene.ts`

**Acceptance:**
- BootScene's 800ms "mathBasher" title display becomes redundant once the splash also shows the title — remove or shorten the BootScene title to a half-second branded splash with NO title text (just the slate background) so the transition from splash to gameplay feels instant
- Decision: KEEP a brief BootScene render (250ms) so the AttributionScene + MenuScene have a moment to initialize, but DROP the title text. A future polish sprint could replace this with a proper loading bar.
- Update the inline comment in BootScene explaining the new shorter timing

### Story 4: Optional `?autostart` URL param for dev workflow

**Type:** Code
**Output:** `src/main.ts`

**Acceptance:**
- If `window.location.search` contains `autostart=1` (or just `autostart`), the splash button is auto-clicked on page load
- This restores the pre-0.5.4 behavior for developers iterating with HMR (no extra click per page refresh)
- Production users never see the autostart param; it's a dev-convenience feature
- Documented in DeveloperGuide.md's quick-start section
- If both `?autostart` and the splash are visible briefly (race condition), the splash dismisses cleanly within ~50ms

### Story 5: Wire button-click SFX to every PlaceholderButton

**Type:** Code
**Output:** `src/core/audioKeys.ts` (new SfxKey entry); `src/game/scenes/BootScene.ts` (preload); `src/game/ui/PlaceholderButton.ts` (play in onClick path); possibly `src/game/scenes/HudScene.ts` (Pause + Mute icon buttons since they're not PlaceholderButtons)

**Acceptance:**
- New `SfxKeys.ButtonClick1 = 'button-click-1'` added to `audioKeys.ts`
- BootScene's preload list grows to include the new asset (count log goes 4 → 5)
- `PlaceholderButton` plays `button-click-1` via `getAudioManager().play(SfxKeys.ButtonClick1, 'sfx')` on every `onClick` activation — pointer click AND keyboard activation (Enter/Space when focused). Disabled buttons still suppress (no audio when disabled).
- The HUD's custom Pause + Mute icon buttons (which are not PlaceholderButtons) ALSO play the click sound when activated. Same call site pattern.
- The splash's "Tap to play" button (Story 1) plays the click sound on its activation. This is the **first** time audio plays in the page lifetime, so it's also a real-world test of the iOS first-gesture audio context resume.
- Volume tracks the existing **sfx** slider — no new slider needed (button clicks are sfx by category).
- Mute respected — mute toggle silences clicks too.
- **Acceptance edge case**: clicking the **mute button itself** to UNMUTE should NOT fire a click sound (volume is 0 at the moment of activation). Clicking it to MUTE WILL fire the click sound (volume is still > 0 when the click happens, since `setMuted(true)` runs after the play call). Acceptable; could be tightened later if it sounds odd.
- **No SettingsScene volume slider for "UI sounds" specifically** — UI clicks ride on the sfx slider. If a future user complains "I want game SFX loud but UI quiet" we'd add a fourth kind. Not now.

## Notes for Claude Code

- **The change is small but architecturally meaningful.** Top-level `new Phaser.Game(...)` → click-handler-bound construction. Once made, the boot is irreversibly gesture-bound; any future contributor who tries to put construction back at top-level should be caught by the test in Story 5.
- **Don't break the AudioManager singleton's eager init.** Currently `createAudioManager()` is called at top-level in `main.ts`. After this sprint it should still be called early — but inside `startGame()` (before Phaser.Game) so the manager is ready when scenes start. Mute state from localStorage needs to be loaded before HudScene renders.
- **Splash CSS belongs in `index.html` inline OR a tiny `src/styles.css`** — DON'T pull a CSS framework. The splash is ~30 lines of CSS; framework overhead would dwarf the actual content.
- **Don't show a loading bar yet.** Asset preload finishes in <100ms today. A loading bar would be visible for one frame, which is worse than nothing. When asset count grows (animation atlases, music tracks, etc.), revisit.
- **Browser-tab title** — the splash is a chance to verify `<title>mathBasher</title>` is set in `index.html`. Should already be, but worth confirming.
- **The AudioContext warning** that triggered this sprint is a Firefox + Chrome browser-level warning, not a Phaser thing. We're working around it by giving the browser the user gesture it expects before the AudioContext is created.
- **WebGL warnings** (`Alpha-premult and y-flip are deprecated`, `generateMipmap incurring lazy initialization`) are SEPARATE from this sprint. They're Phaser's internal WebGL behavior, Firefox-only, harmless. Not addressed by 0.5.4. If we ever care, that's its own investigation (likely "switch off Firefox dev warnings" or "wait for Phaser to update its texture upload paths").
