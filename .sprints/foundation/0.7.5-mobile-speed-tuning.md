## Stories

### Story 1: Mobile font size bump

**Type:** Code (typography tuning)
**Output:** Bump the font sizes used at small viewports so the Baloo 2 typography (introduced in 0.7 Story 7) reads cleanly on phone-sized devices. Most of the in-game text is sized in design-canvas pixels (1280×720) — when FIT-scaled to a phone's ~640×360 device viewport, those design-px sizes effectively halve. Some text was readable on desktop but uncomfortable on phone.

**Acceptance:**
- Identify the in-game text elements that read too small on phone (HUD score, prompt, counter, alien answer numbers, GameOver score, footer attribution, button labels). Either:
  - **(a) Universal bump** — increase every `fontSize` literal across the typography vocabulary by ~20%, OR
  - **(b) Targeted bumps** — pick the specific elements that are too small (likely the 12px footer + 18px HUD items + 14px button labels) and bump those.
- Verify on Firefox responsive design mode at iPhone 14 Pro (393×852 @ DPR 3), Galaxy S20 (412×915), iPad Air (1180×820 landscape).
- Verify the bumped sizes don't break layout — HUD bar still fits its three labels + 2 icons; alien block answer text still fits its 80×60 chassis; footer text still fits the 28px-tall AGPL §7(b) strip.

**Implementation note:** the cleanest path is option (a) via the `STYLES` registry in `src/game/ui/typography.ts` — bump every `fontSize` value by 20% (e.g. `'12px'` → `'14px'`, `'18px'` → `'22px'`, `'24px'` → `'28px'`) and verify all scenes still lay out correctly. If layout breaks, drop to option (b).

### Story 2: Shooter speed +25%

**Type:** Code (config tuning)
**Output:** Bump `config.hero.runSpeedPxPerSec` from 253 → 316 (+25%). Falling block descent speeds (`config.scoring.speed.{slow,medium,fast}.descentPxPerSec`) **unchanged** — explicit constraint per the user request.

**Acceptance:**
- Single line edit in `src/core/config.ts`: `runSpeedPxPerSec: 253` → `runSpeedPxPerSec: 316` (or the math: `Math.round(253 * 1.25) = 316`).
- Tuning history comment in the file updated to reflect the v0.7.5 bump (matches the `v0.6.3 +15%` and `v0.5 baseline 220` entries already there).
- No regression on TouchFireButton / pause / hit detection (none of those depend on hero speed).

**Why this exists:**
The 0.6.3 +15% bump (220 → 253) helped the "shooter can't physically traverse to the right answer in time" pain, but per playtest, the shooter still feels too slow against the (also-fast) falling blocks. +25% from current 253 = 316 px/s. Cumulative effect from v0.5 baseline:
  - v0.5 baseline: 220 px/s
  - v0.6.3 +15%: 253 (1.15× baseline)
  - v0.7.5 +25%: 316 (1.44× baseline overall)

If 316 ends up too zippy, the same line edit walks it back. Falling block speed is independent — sprint 0.6 settled `slow:41 / medium:62 / fast:93 px/s descent` and those stay locked.

### Story 4 — Button-click telemetry

**Type:** Instrumentation (no UI / behavior change)

**Output:**
- New telemetry event `ButtonClicked` (severity `Information`) emitted from every successful button activation in the app
- Properties on every emission:
  - `label` — the button's text (e.g. `"Resume"`, `"Settings"`, `"FIRE"`, `"Back"`, `"−"`, `"+"`)
  - `sceneKey` — `scene.scene.key` of the active scene (distinguishes a "Back" in Settings from a "Back" in DifficultyScene)
  - `source` — `"pointer" | "keyboard"` (touch/mouse vs. Tab+Enter)
- `PlaceholderButton` covers all menu / overlay / settings buttons (single chokepoint via `playClickSfx`-adjacent helper); emit BEFORE invoking `onClick` so the event fires even if `onClick` throws
- `TouchFireButton` covers the on-screen FIRE button; emit BEFORE `opts.onFire()` for the same reason
- `TelemetryPropName` union (or equivalent typing) extended with `'label'`, `'sceneKey'`, `'source'` if not already present
- Disabled buttons continue to no-op (no SFX, no `onClick`, and no telemetry — matches existing behavior)

**Acceptance:**
- Manual: click any button in any scene → `ButtonClicked` appears in console (and App Insights when configured) with the three properties populated correctly
- Manual: Tab to a focused button + press Enter → same event, `source: 'keyboard'`
- Manual: click a disabled button (e.g. `−` at 0% volume in Settings) → NO event emitted
- Unit test added (`PlaceholderButton.test.ts` or `telemetry.test.ts`) that mocks `_th.logToAi` and asserts it is called once per `pointerdown` AND once per `activate()`, with the expected shape
- `pnpm typecheck` and `pnpm test` green

**Why this exists:**
Per CLAUDE.md ("every meaningful action is tracked"), button clicks are the canonical user action — yet today the telemetry stream goes silent on what the user clicked between scene-start/scene-complete events. Funnels (e.g. "what fraction of MenuScene visitors actually hit Start vs. wander to Settings vs. abandon?") are unanswerable. This story closes the gap with a single event shared across the two button widgets in the codebase.

**Decision: keep `ButtonClicked` separate from `Fire` (or whatever InputSystem emits).**
The FIRE button emits BOTH events when tapped. `ButtonClicked` is the UI-intent event ("user pressed a UI control labeled FIRE"); the InputSystem-level event is the gameplay event ("a shot was fired"). They have different downstream consumers — UI funnels vs. gameplay analytics — and conflating them would force every dashboard to filter by source. The duplicate emission is the correct shape, not noise.

**Out of scope (call-out for reviewer):**
- Tracking *disabled-button clicks* as a frustration signal — would be its own event (`DisabledButtonClicked`), not in this story
- Tracking *hover-but-no-click* / abandonment — interesting but heavyweight; defer

**Type:** UI tweak (no behavioral change)

**Output:**

4. **Pronounced section labels.** TextKind `sectionLabel` updated: 24px muted → 32px primary bold. Affects "Math Type" and "Speed" in DifficultyScene AND "Volume" in SettingsScene (deliberate — the same heading-treatment bump improves both screens).

**Acceptance:**
- Manual: open DifficultyScene → "Two numbers, sum at most 10." renders fully inside its tile (no overflow)
- Manual: "Math Type" and "Speed" labels read as clear section dividers (large + bright + bold)
- Manual: "Volume" label in SettingsScene gets the same heading treatment (acceptable side-effect)
- `pnpm typecheck` / `pnpm test` / `pnpm build` green

**Why this exists:**
Story 1's universal font bump made all the tile labels and subtitles bigger but didn't re-tune the container dimensions to match. This is the standard pattern after a font scale change — tighten layout, re-flow long text, re-balance section spacing. The section-label change is independent feedback from playtest ("the headers are too quiet").

**Out of scope:**

- Moving "Coming soon." text into a tooltip or modal (keep it inline; "Coming soon." reads fine in the wider tile)

### Story 6 — Halve music gain across the entire slider range

**Type:** Audio tuning (no UI change)

**Origin:** 0.7.5 playtest. Music at the SettingsScene 10% slider position is still too loud against SFX + midground. The fix is to globally squash the music scale — what currently plays at 50% slider becomes the new max output.

**Output:**
- Add a per-kind attenuation factor inside `AudioManager.effectiveVolume01`. Music gets `0.5×`; sfx and midground stay `1.0×` (untouched).
- The slider, the displayed percent in SettingsScene, and the persisted localStorage value all stay on the 0–100 user-facing scale. The attenuation is invisible to the SettingsScene UI — only the gain handed to Phaser's sound API is halved for music.
- Update the one test that asserts effective volume (`AudioManager.test.ts` line ~252) for music: `slider 80 → effective 0.4` (was 0.8).
- Add a new test that locks in the music-only attenuation: at slider 100, music effective = 0.5 while sfx + midground effective = 1.0.

**Acceptance:**
- Manual: open Settings, set music to 100% → audibly equals the loudness music played at 50% before this story
- Manual: at music 10%, music is now noticeably quieter than the prior 10% (audibly halved)
- Manual: sfx and midground sliders behave identically to before
- `AudioManager.test.ts` covers the new attenuation rule
- `pnpm typecheck` / `pnpm test` / `pnpm build` green

**Why this exists:**
The encoder's per-kind LUFS targets (-16 sfx / -22 midground / -18 music) plus the default sliders (70 / 40 / 50) were tuned together pre-Story 0.7's actual music tracks landing. Once real music files were placed in `public/assets/audio/music/`, the music turned out to sit louder than the LUFS pass implied (likely because the chosen tracks have heavy low-end energy that LUFS slightly under-counts perceptually). Re-encoding every music file at -24 LUFS would also work, but a single-line code attenuation:
  - is reversible (delete one constant entry → music goes back to current scale)
  - doesn't require re-running the audio pipeline + checking each track in
  - lets the existing slider scale + persisted user preferences work unchanged

If the per-kind attenuation table grows beyond music (e.g. midground also needs squashing), it becomes a natural place to lift to `config.scoring.audio` or similar in a future sprint.

**Out of scope:**
- Re-encoding music files at a lower LUFS target (declined; one-line code change is cheaper and reversible)
- Adding a `musicAttenuation` knob to SettingsScene (this is a balance fix, not a user-facing preference)
- Touching the `sfx` or `midground` scales (user explicitly scoped this to music only)
