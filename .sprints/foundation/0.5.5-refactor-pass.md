# Sprint 0.5.5: Refactor Pass

**Phase:** Foundation
**Status:** Closed (2026-05-09)
**Released:** v0.5.5
**Blocks:** 0.6 Mobile + responsive
**Depends on:** 0.5.4 Click-to-start splash + button-click SFX
**Estimated effort:** 1 day

## Summary

A focused, **purely-internal** refactor sprint. Zero new user-visible behavior. Goal: collapse accumulated duplication and tighten module boundaries before Phase 1 mobile-responsive work begins, so the mobile sprint can change one place per concern instead of six.

This sprint is the direct output of an Architect + Senior Dev codebase audit run at the wrap of 0.5.4. Both reviewers independently flagged the same top items: scene-create boilerplate hoist, IconButton extraction, boot orchestration split, layout helper, audio manifest, typography centralization. The 8 stories below map 1:1 to the audit's findings A through H.

**Non-goals.** No new features, no asset additions, no telemetry-event additions, no behavior changes. Every PlaceholderButton must look and click identically post-refactor. The full test suite (96 tests today) MUST stay green after every story; no test deletions, only test refactors when the helper they reference moves.

**Success criterion.** A future contributor adding a new menu scene writes 30% less boilerplate than today, and a "change the menu button width" / "change the title font" / "add a fourth audio-kind" change is a 1-file edit.

## Stories

### Story A: Extract `BaseMenuScene` for shared scene-create boilerplate

**Type:** Code
**Output:** `src/game/scenes/BaseMenuScene.ts` (new), edits to `MenuScene`, `GameSelectScene`, `DifficultyScene`, `GameOverScene`, `GameScene`

**What's wrong.** Five scenes open `create()` with the same shape: `_th.logToAi('XScene Started', ...)` + `getAudioManager().init(this)` + later `... 'XScene Completed' ...`. PlaceholderButton's pointerdown click-SFX path needs a fresh scene binding in every scene; the line is copy-pasted in 5 places today.

**Acceptance:**
- New `BaseMenuScene extends Phaser.Scene` provides a `create()` (or a `protected setupScene()` helper) that:
  1. Logs `'<sceneKey> Started'` (Information)
  2. Calls `getAudioManager().init(this)`
  3. Registers a `shutdown` listener that logs `'<sceneKey> Completed'`
- Subclasses migrate to either `extends BaseMenuScene` (and `super.create()` first) OR explicit `this.setupScene()` first call — pick whichever pattern reads cleanest given Phaser's scene lifecycle (the spike will tell us).
- `GameScene` is included in the migration even though it's not strictly a "menu" scene — it shares the same boilerplate. Either rename `BaseMenuScene` → `BaseSceneWithAudio` if the menu connotation feels wrong, or keep `BaseMenuScene` and accept GameScene as the sole non-menu user with a comment explaining why.
- All existing scene-specific telemetry (e.g. `GameOverScene`'s extra `props` on its Started event) must still work — the base class's logging must be overridable or composable.
- Every `getAudioManager().init(this)` call previously added in 0.5.4 follow-up is removed from the subclass and now lives only in the base.
- `pnpm test` 96/96 passing; no test deletions.

### Story B: Extract `IconButton` + co-located `uiPalette.ts`

**Type:** Code
**Output:** `src/game/ui/IconButton.ts` (new), `src/game/ui/uiPalette.ts` (new), heavy edit to `src/game/scenes/HudScene.ts`

**What's wrong.** `createPauseButton` and `createMuteButton` in `HudScene.ts` are two ~40-line blocks with ~80% identical structure: container + 44×36 bg rectangle + stroke + hover/focus/repaint logic + Focusable shim. The HudScene comment said "wait for 3rd caller before extracting" — but with two near-identical 40-line blocks IN THE SAME FILE the rule-of-three threshold is already crossed within HudScene itself.

**Acceptance:**
- New `IconButton extends Phaser.GameObjects.Container` accepts `{ scene, x, y, width, height, render: (container) => void, onActivate, ariaLabel, focusable }`.
- The `render` callback paints the icon glyph (pause bars OR speaker emoji); the wrapper owns bg + border + hover repaint + focus repaint + click SFX + Focusable shim.
- `uiPalette.ts` exports the four button-state colors as named constants (`SLATE_BG`, `SLATE_HOVER`, `BORDER_GREY`, `FOCUS_BLUE`, `SELECTED_AMBER`, `DISABLED_BG`) — same hexes used by `PlaceholderButton`. Both `IconButton` and `PlaceholderButton` import from `uiPalette`.
- HudScene's `createPauseButton` and `createMuteButton` shrink to ~10 lines each (just the glyph render + the activate handler).
- Visual + behavioral parity: the Pause and Mute icons look pixel-identical and behave identically post-refactor (hover, focus, click SFX, mute-toggle).

### Story C: Move boot orchestration to `src/app/boot.ts`

**Type:** Code
**Output:** `src/app/boot.ts` (new), heavy slim of `src/main.ts`, edit `src/main.test.ts` if needed

**What's wrong.** `main.ts` is now ~120 lines doing 4 jobs: telemetry init, splash button wiring, Phaser game construction, dev `?autostart` shortcut. Phase 1 will likely add an asset-preload progress bar, screen-orientation gate, and maybe a "WebAudio unsupported" fallback — `main.ts` will hit 250+ lines doing 7 jobs.

**Acceptance:**
- `src/app/boot.ts` exports a `bootGame()` function that contains the full Phaser construction + scene list + the splash-hide logic.
- `src/main.ts` shrinks to ~15 lines: telemetry init, splash button wiring, autostart shortcut, calling `bootGame()`.
- `src/main.test.ts` continues to pass — its three tests scan `main.ts` source for the deferred-construction pattern. Either:
  - Update the test to scan `boot.ts` instead (re-anchor the contract to wherever the construction now lives), OR
  - Keep the test on `main.ts` and add a new contract test that `main.ts` does NOT itself import Phaser (the import moves to `boot.ts`).
  - Pick whichever framing better captures the architectural rule "Phaser constructed inside a user gesture; never at module load."
- The 250ms BootScene wait + every other downstream behavior is unchanged.

### Story D: `MenuLayout` helper + `config.layout.button` constants

**Type:** Code
**Output:** `src/game/ui/MenuLayout.ts` (new), edit `src/core/config.ts`, edits to scenes that stack buttons

**What's wrong.** Every menu scene re-derives `const { width, height } = this.scale; const cx = width / 2;` and hand-codes `y: height * 0.5`, `0.62`, `0.74` etc. Button widths (200/240/280) and heights (56/64) are sprinkled throughout — no shared rhythm, and a "make all primary buttons 320 wide" change is a 6-file edit.

**Acceptance:**
- `config.ts` gains a `layout.button` block: `{ primaryW: 280, primaryH: 64, secondaryW: 200, secondaryH: 56, tileW: 320, tileH: 200 }` (final numbers picked from the existing scene values).
- `MenuLayout.ts` exports a `stackButtons(scene, { centerY, gap, items: [{label, onClick, kind?: 'primary' | 'secondary'}] })` helper that constructs buttons in a vertical stack and returns them in tab order.
- At least three scenes migrate to use it: `MenuScene`, `PauseOverlay`, `GameOverScene` (the cleanest stacked-button cases). `DifficultyScene` and `GameSelectScene` use grid layouts and are out of scope; they MAY adopt the constants from `config.layout.button` even if they don't use the stack helper.
- Visual parity: y-coordinates of stacked buttons are within 4px of pre-refactor positions (a deliberate small drift to land on a clean rhythm is fine; a large jump is not).

### Story E: `AUDIO_MANIFEST` derivation in `audioKeys.ts`

**Type:** Code
**Output:** edit `src/core/audioKeys.ts`, slim `src/game/scenes/BootScene.ts`

**What's wrong.** `BootScene.preload` builds a `[key, path]` tuple list by hand-pairing every `SfxKeys` / `MidgroundKeys` / `MusicKeys` entry with its path helper. The CLAUDE comment in BootScene calls it "the single source of truth," but the list lives in BootScene, not audioKeys. Adding a new sound is a 2-file change today (audioKeys + BootScene).

**Acceptance:**
- `audioKeys.ts` exports an `AUDIO_MANIFEST: ReadonlyArray<{ key: string; kind: AudioKind; url: string }>` derived programmatically from the three key objects, e.g. `Object.values(SfxKeys).map(k => ({ key: k, kind: 'sfx', url: sfxPath(k) }))` ... etc.
- `BootScene.preload` becomes `for (const a of AUDIO_MANIFEST) this.load.audio(a.key, a.url);` with no per-kind branching.
- The preload-count log derives from `AUDIO_MANIFEST.length`, NOT a hardcoded number.
- Adding a new SFX key (the verification test) requires editing only `audioKeys.ts`; BootScene needs zero changes.
- All five existing assets still preload; PLAYTEST `BootScene PreloadedSfx` log shows `reason: '5'`.

### Story F: `typography.ts` for fonts + extend `uiPalette.ts` for global colors

**Type:** Code
**Output:** `src/game/ui/typography.ts` (new), edit `src/game/ui/uiPalette.ts`, edits across scenes

**What's wrong.** `'system-ui, sans-serif'` appears in 40+ places. The hex palette (`#eaeaf2`, `#9ca3af`, `#facc15`, `#34d399`, `#fbbf24`, `#60a5fa`) is scattered through scene files. A future "title font is now Comic Neue" change is a 40-file find/replace.

**Acceptance:**
- `typography.ts` exports `FONT_FAMILY` constant + a `text(scene, x, y, str, kind)` helper where kind is one of `'title' | 'h2' | 'body' | 'subtitle' | 'accent'`.
- `uiPalette.ts` (created in Story B) extends with text-color constants: `TEXT_PRIMARY`, `TEXT_MUTED`, `TEXT_AMBER`, `TEXT_GREEN`, `TEXT_RED` etc. — same hexes, named.
- At least every scene's PRIMARY title text + subtitle uses `text(...)` — `MenuScene`, `GameSelectScene`, `DifficultyScene`, `GameOverScene`, `PauseOverlay`, `SettingsScene`, `BootScene`. Body strings inside button labels are NOT in scope (PlaceholderButton owns its own text).
- The `'system-ui, sans-serif'` literal does not appear outside `typography.ts` (verified by `grep` post-refactor — it's allowed exactly once).

### Story H: Tighten type casts at facade boundaries

**Type:** Code
**Output:** edits to `PhaserAudioManager.ts`, `KeyboardNavigator.ts`, possibly `HudScene.getGameScene`

**What's wrong.** Several `as` casts hide small lies at typed boundaries: `PhaserAudioManager.init(scene: unknown)` then casts to `Phaser.Scene`; `KeyboardNavigator` does `{} as Phaser.Input.Keyboard.Key`; `HudScene.getGameScene` casts to `GameScene | null`; `applyVolume` does `(sound as Phaser.Sound.BaseSound & { setVolume(v: number): void })`.

**Acceptance:**
- `PhaserAudioManager.init` accepts `Phaser.Scene` directly (the "pure facade can't import Phaser" claim is already broken in `PhaserAudioManager` itself; tightening here is honest). The base `AudioManager.init` keeps `unknown` so pure callers don't pull Phaser into their import graph.
- `KeyboardNavigator`'s `{} as Key` placeholder gets a real lazy initializer or its type relaxes to `Key | undefined`.
- `applyVolume`'s setVolume cast is documented (the BaseSound type genuinely doesn't expose setVolume) — wrap in a single helper with a one-line comment explaining why the cast is necessary; don't widen further.
- No new `any` is introduced; `pnpm tsc --noEmit` stays clean.
