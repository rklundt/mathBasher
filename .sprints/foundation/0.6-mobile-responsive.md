# Sprint 0.6: Mobile + Responsive

**Phase:** Foundation
**Status:** Closed (2026-05-10)
**Released:** v0.6
**Blocks:** 0.7 Art polish
**Depends on:** 0.5.5 Refactor pass
**Estimated effort:** 0.5-1 day

## Summary

Make the game playable in landscape on a phone. Two main pieces: (1) a responsive scaling strategy that handles every reasonable landscape aspect ratio without clipping or whitespace surprises, and (2) an on-screen fire button for touch devices that doesn't interfere with mouse/keyboard play on desktop.

## Stories

### Story 1: Scale strategy decision and config

**Type:** Code/data definition
**Output:** Update `src/main.ts` Phaser game config; document the decision in `src/core/SCALE.md` (a brief inline note, NOT a polished doc)
**Acceptance:**
- Use `Phaser.Scale.FIT` with a 16:9 design canvas (1280x720) by default — letterboxing on aspect ratios different from 16:9
- Add `scale.expandParent: true`, `scale.parent: 'game'`
- The page CSS makes `<div id="game">` fill `100vw x 100vh` with no scrollbars; black background outside the canvas hides letterboxing seams
- Page is locked to landscape on mobile via CSS rotation prompt (a fixed overlay shown only when portrait is detected, advising to rotate). The overlay covers everything; no in-game UI is reachable until the device returns to landscape.
- The decision (FIT + 16:9 + landscape lock) is recorded in `src/core/SCALE.md` in 5-10 lines so future contributors don't have to guess.

### Story 2: Portrait-rotate overlay

**Type:** Code
**Output:** `app/index.html` (CSS + tiny inline DOM), `src/main.ts` (orientation listener)
**Acceptance:**
- A `<div id="rotate-overlay">` sits over the game canvas, hidden by default
- A media query `@media (orientation: portrait) and (max-width: 900px)` shows it
- Inside: an icon (CSS-only is fine — a rotated phone glyph) and text "Please rotate your device to landscape to play."
- When the orientation changes back, the overlay hides and Phaser receives a resize event so it re-fits

### Story 3: Touch fire button (visible on touch devices)

**Type:** Code
**Output:** `src/game/ui/TouchFireButton.ts`, integrated into `GameScene` and (optionally) `MenuScene` for an "OK" button if needed
**Acceptance:**
- A round button anchored bottom-right (with safe-area padding from `config.layout.safeAreaPaddingPx`)
- **Positioned ABOVE the AttributionScene footer**, never overlapping it. The footer sits at the very bottom; the fire button sits above the footer with at least 8px of clearance.
- Hidden on devices where `navigator.maxTouchPoints === 0` AND there's no recent touch input; shown if either condition flips. (Belt-and-braces: touch laptops still get the button, kids on a touchscreen Surface still play correctly.)
- Pointer-down emits `'fire'` through the existing `InputSystem` -> same code path as Space / click
- Visual press state (slightly smaller / brighter) on `pointerdown`
- Hit area is generous (at least 64x64 device-independent px)

### Story 4: Tap-anywhere fire is preserved (with one carve-out)

**Type:** Code
**Output:** Update `InputSystem`
**Acceptance:**
- Tap anywhere on canvas still fires (carry-over from 0.5)
- Carve-out: pointer-down events whose target is the TouchFireButton container are not double-counted (button's own handler does the work, and event propagation is stopped)
- Pointer-down events on UI buttons in non-game scenes (Menu, Difficulty, etc.) are NOT treated as fire — InputSystem only listens while GameScene is active

### Story 5: Layout review pass

**Type:** Test
**Output:** Manual checklist appended to `src/game/PLAYTEST.md`
**Acceptance:** Verified manually at the following viewports (use Chrome DevTools device toolbar):
- iPhone SE landscape (667x375)
- iPhone 14 Pro landscape (852x393)
- iPad Mini landscape (1024x768)
- 1280x720 desktop
- 1920x1080 desktop
- Ultra-wide 21:9 (e.g. 2560x1080)

For each: no clipping of the hero or aliens, no off-canvas text, fire button reachable with thumb in landscape, prompt readable, AttributionScene footer visible and not overlapping the fire button.

### Story 6: Performance sanity

**Type:** Test
**Output:** Note in PLAYTEST.md
**Acceptance:**
- Frame rate stays above ~50fps on a mid-tier Android (or use Chrome's CPU throttling at 4x slowdown to approximate) during a full round
- No console warnings about object pooling or texture limits

### Story 8: Speed re-tune (added late from playtest feedback)

**Type:** Code (one-knob tuning change; not a refactor but bundled into the sprint because the playtest that drove it was this sprint's playtest)
**Output:** edit `src/core/config.ts`; refresh PLAYTEST.md row

**What's wrong.** Playtest of the v0.5.5 speeds during sprint 0.6 mobile testing surfaced: "the blocks fall too fast — if I get the answer wrong but I'm still thinking, I don't have enough time for the blaster to make it back for a final pass." The two +10% passes from sprint 0.5.5 overshot the kid-friendly mark.

**Acceptance:**
- All three tiers' descent + penalty rates pulled back -15%:
  - slow: descent 48 → 41; penalty 145 → 123
  - medium: descent 73 → 62; penalty 218 → 185
  - fast: descent 109 → 93; penalty 327 → 278
- Score multipliers per tier UNCHANGED (still 1.0 / 1.25 / 1.5).
- Cumulative effect from v0.5.4 baseline: `1.10 × 1.10 × 0.85 ≈ 1.03` — effectively neutral (~3% above original baseline). The two +10% passes from sprint 0.5.5 over-corrected; this -15% pulls it back near baseline.
- Comment block in `config.ts` records the full tuning history (newest first) + an explicit how-to-rebalance hint so a future contributor knows the right knob.
- PLAYTEST.md sprint-0.5.5 speed-tuning row updated with the new numbers + cumulative-effect note (was: "21% faster than v0.5.4"; now: "~3% above baseline, effectively neutral").
- Tuning is centralized — all six numbers live under `config.scoring.speed.{slow,medium,fast}.{descentPxPerSec,penaltyPxPerSec}` in one file. Future re-tunes are a 6-number edit; no other code changes.

## Notes for Claude Code

- Phaser's scale modes are well-documented; FIT is the right choice here (preserves aspect, letterboxes). Don't try `RESIZE` — it complicates entity layout for no real win on a fixed-viewport game.
- The portrait overlay is DOM, not Phaser. That's fine. It's the simplest place to handle it.
- Don't reinvent input plumbing. The TouchFireButton is just a UI element that calls into InputSystem, not a parallel input pathway.
- Test on a real phone if possible. DevTools device emulation gets the layout right but does not represent touch latency or thumb ergonomics.
