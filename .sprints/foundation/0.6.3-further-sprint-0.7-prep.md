# Sprint 0.6.3: Further Sprint 0.7 Prep

**Phase:** Foundation
**Status:** Closed (2026-05-12)
**Released:** v0.6.3
**Blocks:** 0.7 Art polish
**Depends on:** 0.6.2 Sprint 0.7 decisions
**Estimated effort:** 0.5–1 day (actual: ~2 days — mid-sprint scope grew from 3 stories → 7 after playtest surfaced quality issues + a math bug)

## Summary

A third bridge sprint between 0.6.x and 0.7. Where 0.6.2 produced *decisions* about how sprites get extracted and organized, 0.6.3 takes those extracted sprites and **wires them into the gameplay loop** so we can field-test them before committing to final curation in 0.7. Also folds in two gameplay-feel tweaks that surfaced during the same playtesting session.

This is the "kick the tires before you build the showroom" sprint — by the time 0.7 starts, we'll know whether the sprite-on-block pattern actually feels good in motion, and the shooter+jiggle tuning will have been validated against real play.

Seven discrete stories. None blocks the others; all seven should land in the same PR. (Stories 4–7 were added mid-sprint after surfacing during playtest / diagnostic.)

## Stories

### Story 1: Random animated sprite on each falling number block

**Type:** Code (BootScene + Wave/Alien spawn)
**Output:**
- Asset loader: `BootScene.preload()` loads all alien spritesheets from the picked tier subfolder per ADR-0010. Use the 45 curated-pool keys produced in 0.6.2 (`alien1-r0c0` … `alien5-r2c2`).
- New helper: `pickSpriteTier(viewportWidth, devicePixelRatio): '128' | '192'` in `src/core/` (boot-time, called once).
- Asset key registry: `src/core/assetKeys.ts` exports `ALIEN_SPRITE_KEYS: readonly string[]` so the spawn code doesn't string-pun.
- Each falling number block gets a randomly-selected alien sprite layered ON TOP of the number block (above the number text in z-order, sized to roughly match the block — don't overflow).
- Sprite animates through all 63 frames at 12 fps in a loop, continuing through the entire descent.
- Pick is per-block (each new block in a wave gets its own random sprite — same answer can wear different faces).
- Random pick uses a seeded PRNG if one is already in the codebase; otherwise `Math.random()` is fine for this sprint.

**Acceptance:**
- Sprites visible on every falling block, both 128 tier (when on phone/tablet viewport) and 192 tier (when on desktop).
- Animation runs smoothly (no obvious stutter or frame-skip) on a typical desktop browser.
- Block + sprite remain visually coherent during descent (sprite tracks the block, no decoupling).
- Number text on the block is still readable — sprite layered above the BG fill but text still visible (either text in front of sprite, or sprite positioned to not occlude text — implementer's judgment).
- No console errors on missing assets.
- Wave-clear behavior unchanged: when a block is hit (correct or wrong), its sprite goes away with it — no lingering sprites.

**Implementer notes:**
- The 45-key pool may include some sprites that don't look great in motion. Don't curate during this sprint — that's 0.7 Story 4. Even the not-great ones should display correctly during this sprint.
- Phaser supports atlas-based animation playback. Each WebP is a horizontal-row spritesheet of 63 frames at `cellSize × cellSize`, so frame-width = cellSize, frame-count = 63. Phaser's `anims.create({ frames: anims.generateFrameNumbers(...) })` pattern fits.
- If a sprite's natural aspect doesn't match the block aspect, scale to fit the block's smaller dimension (don't stretch).

### Story 2: Shooter speed +15%

**Type:** Code (config tuning)
**Output:**
- Hero (the yellow block / shooter) horizontal movement speed bumped by 15% from current value.
- Update the relevant constant in `src/core/config.ts` (likely under `gameplay` or similar).
- Falling block descent rate **unchanged** — the -15% pulled-back speed from sprint 0.6 stays exactly where it is. Only the shooter speed moves.

**Acceptance:**
- Shooter clearly responsive at the new speed when playtested. The "I want to shoot but the shooter can't get to the right answer in time" pain from current builds is reduced.
- Block descent rate verified unchanged via playtest comparison (or by reading the config diff — only one constant moves).
- No regression on touch-control feel (TouchFireButton ergonomics still work — shooter speed change doesn't break the touch input model).

**Why this exists:**
The -15% block speed re-tune in sprint 0.6 helped the "I'm thinking but the answer just landed" failure mode, but didn't address the related "the shooter can't physically traverse to the right answer in time" issue. Increasing shooter speed by 15% should restore the player's ability to commit to an answer once they've decided.

### Story 3: 1-second pre-fall "jiggle" so the player can read the equation

**Type:** Code (Wave / per-question lifecycle)
**Output:**
- New phase in the per-question lifecycle: when a new wave/question spawns, the falling blocks appear at their starting positions and **jiggle in place** for 1 second before starting to descend.
- Jiggle = small left-right oscillation, a few pixels (3–5 px in design-canvas space). Like a block "coming loose" before falling.
- All blocks in the wave jiggle in unison (or staggered by a small phase — implementer's judgment, but keep it cohesive).
- After the 1-second jiggle, blocks transition smoothly into their normal descent. No discontinuity at the handoff.
- Per question — every new wave/question gets its own 1-second jiggle preamble.

**Acceptance:**
- Player has a clear ~1-second window to read the question text + see the answer options before any block starts descending.
- Jiggle is subtle enough that it doesn't feel "broken" — reads as anticipation, not a glitch.
- Pause + Esc behavior during the jiggle is consistent with pause behavior during fall (jiggle pauses cleanly, resumes cleanly).
- No visual stutter at the jiggle-to-fall transition.

**Implementer notes:**
- Phaser tweens with `yoyo: true, repeat: -1` on a small x-offset, then stopped + cleared at the 1-second mark, is the simple path.
- The 1-second timer should be adjustable via config (don't hard-code) — folks may want to tune to 0.75s or 1.25s based on playtesting feedback.
- Telemetry: log the question-spawn → fall-start delta so we can A/B test the jiggle duration if needed.

### Story 4: Loading bar in BootScene during sprite preload

**Type:** Code (BootScene UI)
**Output:**
- Visible loading indicator rendered in `BootScene.preload()` / `create()` — shown during the 45-spritesheet preload (~10-20 MB depending on tier).
- Progress bar that fills 0% → 100% as Phaser's loader fires `load.on('progress', ...)`.
- A "Loading..." label below the bar for clarity.
- Color scheme matches the existing slate background of the HTML splash (`#1e293b` / `#0f172a` palette) so the splash → boot transition reads as continuous, not a jarring flash.
- Existing 250ms `delayedCall` in `BootScene.create()` becomes unnecessary once the loading bar is doing the visible-content job, per the comment already in `create()` ("When a real loading bar lands in the art-polish milestone … this delay becomes unnecessary"). Remove it.

**Acceptance:**
- Loading bar appears immediately when BootScene mounts (no flash of empty canvas).
- Bar visibly progresses during sprite preload (catches the eye even on a fast localhost; mandatory on a slow network).
- After load completes, transitions to MenuScene without the prior 250ms artificial delay.
- Bar + label stay readable on both 128-tier (phone) and 192-tier (desktop) loads — design-canvas units, FIT scaled.
- No regression on existing scene-transition behavior (Attribution scene still launches, Menu scene still receives focus).

**Why this exists:**
The 0.5-era boot was instant — only audio (~0.5 MB total). Sprint 0.6.3's 45-spritesheet preload changed that, and a 1-3 second hang with no feedback feels like the app froze. A loading bar is the standard UX for "we're working." Cheap to implement, big perceived-quality lift.

**Implementer notes:**
- Phaser's `load.on('progress', value => ...)` fires with `value` ∈ [0, 1]. Use it to update bar width.
- Bar can be a `Phaser.GameObjects.Rectangle` (background) + a second rectangle (foreground that grows). Simple, no asset needed.
- Center on `scale.gameSize.width / 2`, `gameSize.height / 2` so it's correctly placed regardless of FIT scale.
- The HTML splash uses `bg: #1e293b`, `text: #f1f5f9` — match for visual continuity.

### Story 5: Data-driven sprite-batch registry (add-more-later safety)

**Type:** Code (sprite asset registry)
**Output:**
- `src/core/spriteKeys.ts` rewritten data-driven via a new `ALIEN_SPRITE_BATCHES: readonly AlienSpriteBatch[]` array.
- Each batch entry: `{ prefix: string; rows: number; cols: number }`.
- `ALIEN_SPRITE_KEYS` is now DERIVED from `ALIEN_SPRITE_BATCHES` (was hardcoded as a 5 × 3×3 nested loop = 45 keys).
- Adding a new batch after a `pnpm sprite:extract` run is a one-line append to `ALIEN_SPRITE_BATCHES`. Removing a batch is a one-line delete + removing the sprite files.
- The new pattern mirrors `AUDIO_MANIFEST` in `src/core/audioKeys.ts` (single source of truth, derived counts, no second edit needed in BootScene).

**Acceptance:**
- [x] Both BootScene preload AND `pickRandomAlienSpriteKey()` read from the derived `ALIEN_SPRITE_KEYS` — the new count is picked up automatically when a batch is added or removed.
- [x] Heterogeneous grid dimensions across batches work (e.g. alien1 is 3×3 with 9 cells, alien3 is 3×4 with 12 cells, future batches can be any rows × cols).
- [x] Doc comment on `ALIEN_SPRITE_BATCHES` explicitly tells future-me / future-contributors the "add a batch" workflow.
- [x] Tuning history block on the type captures WHY this is data-driven (so the next session-summary doesn't re-introduce the hardcoded loop).

**Why this exists / problem statement:**

The initial Story 1 implementation hardcoded a `for batch = 1..5; r = 0..2; c = 0..2` loop producing 45 sprite keys. That was correct for the planned 5 source videos × 3×3 grid assumption at sprint kickoff. Three things broke that assumption mid-sprint:

1. **Option C dark-bg pivot.** Halfway through 0.6.3, we re-generated source videos with matched-bg colors to eliminate the white-halo problem. The user re-generated and re-processed videos one at a time; for a stretch only 3 of the 5 batches existed on disk. The hardcoded 45 caused BootScene to 404 on 15 nonexistent assets and `pickRandomAlienSpriteKey()` could pick keys for missing sprites (rendering as blank blocks).
2. **Heterogeneous grid dims.** alien-video-3 came in as a 3×4 grid (12 cells), not 3×3 (9). The hardcoded loop assumed 3×3 for every batch — adding alien3 at 3×4 would have been an awkward special-case.
3. **Future-proofing.** Sprint 0.7's curation pass and beyond will add / remove / re-process batches independently. A registry-as-code pattern means each change is a 1-line edit, not a hunt across BootScene + spawn code + the picker.

**Implementer note (already done):**

Same shape as `audioKeys.ts`'s `AUDIO_MANIFEST` pattern from sprint 0.5.5 — the "single source of truth, derived consumers" pattern is now consistent across audio and sprite registries. If sprint 0.7 introduces hero / projectile / ui / particle / bg sprite kinds, each gets its own `BATCHES` array and derived `KEYS` array following this same template.

### Story 6: Variable-frame-count robustness (BootScene + preview)

**Type:** Code (game-side + tooling)
**Output:**
- **Game-side fix (`src/game/scenes/BootScene.ts`):** stop hardcoding `end: FRAMES_PER_SPRITE - 1` in the per-sprite animation registration. Use Phaser's "all frames in spritesheet" mode (omit `end` from `generateFrameNumbers`) so each sprite's looping animation uses exactly the frames present in its WebP — no extras, no missing.
- **Preview-side fix (`.sprite-source/working/preview.html`):** stop hardcoding `--frames: 63` in CSS. Probe each WebP's natural width on load (`naturalWidth / tier = frame count`), then drive that sprite's animation via the Web Animations API with per-sprite `easing: 'steps(N)'` and matching duration. Each sprite plays at exactly 12 fps over its real frame count, no wrap-around at the spritesheet edge.
- **Docs (`src/core/spriteKeys.ts`):** keep `FRAMES_PER_SPRITE` as the *expected / canonical* frame count for new extracts (still useful as the target source duration when generating new videos), but document that consumers should NOT trust it for animation registration — derive from the actual texture at runtime.

**Acceptance:**
- [x] alien3 (47 frames) plays cleanly in the preview — animation runs for 47/12 ≈ 3.92s then loops, no horizontal-wrap garbage at the end.
- [x] alien1 + alien2 (63 frames) play unchanged at 5.25s loops.
- [x] In-game, any batch's sprite shows continuous cycling regardless of its frame count.
- [x] Any future short / long video Just Works — pipeline produces N frames, code derives N at render time.
- [x] Typecheck clean; all tests pass.

**Why this exists / problem statement:**

The regenerated alien-video-3 had effectively 47 frames per cell instead of 63 (the source video either has VFR encoding that dedups under ffmpeg's `-r 12` filter, or includes repeated frames the pipeline collapses). The pipeline correctly extracted what was there. But two consumers downstream assumed every spritesheet had exactly 63 frames:

1. **Preview CSS** uses a global `--frames: 63` with `steps(63)` over a fixed 5.25s. For a 47-frame WebP, steps 47-62 walk past the end of the image. With CSS `background-repeat: repeat` (default), the bg image wraps back to start mid-animation, producing the "horizontal scrolling" effect the user reported.
2. **Game-side `generateFrameNumbers(key, { start: 0, end: 62 })`** asks Phaser for frames 0-62 from every spritesheet. For a 47-frame WebP, frames 47-62 are out-of-range; Phaser's behavior varies (may use frame 0 as fallback, may skip), but the animation visibly breaks.

The root cause framing matters: even a "perfect" source video pipeline can produce variable-frame-count outputs because ffmpeg's frame-rate filter is allowed to dedup. The system should be robust to that, not assume.

**Implementer notes:**

- Phaser's `generateFrameNumbers(key, { start: 0 })` (omit `end`) defaults to "last frame in the spritesheet." Cleanest fix on the game side.
- The preview's Web Animations API path means we don't need to inject per-sprite `<style>` blocks. Each `Element.animate(...)` call carries its own keyframes + easing + duration — fully self-contained.
- One side benefit: future per-sprite tuning (e.g. one alien plays its animation at 0.5× speed for variety) is now a per-Element property, not a global CSS override.

### Story 7: Math-engine bug fix — uniform answer distribution for add-to-10

**Type:** Code (math generator)
**Output:**
- `src/math/generators/addTo10.ts`: swap the joint-pair sampler for a uniform-over-sums sampler. New algorithm:
  1. Pick `correctAnswer` uniformly from `[0, MAX_SUM]`
  2. Pick `a` uniformly from `[0, correctAnswer]`
  3. `b = correctAnswer - a`
- Update the inline doc comment to reflect the new uniform-over-sums behavior + remove the "v1 acceptable" hedge.
- `src/math/generators/addTo10.test.ts`: extend or replace the existing distribution sanity test to verify each sum 0-10 appears within an expected range (10k iterations, ±20% tolerance per bucket).

**Acceptance:**
- [x] Every sum 0-10 appears with roughly equal frequency (within ±20% of 1/11 ≈ 9.1%) over a 10k-iteration smoke test.
- [x] `a + b === correctAnswer` invariant unchanged.
- [x] `correctAnswer ∈ [0, 10]` invariant unchanged.
- [x] All existing tests still pass — distractors, shuffle, choice count.
- [x] No game-side regression: typecheck clean, full test suite green.

**Problem statement:**

Playtest of sprint 0.6.3 surfaced that the falling-block answer values felt skewed toward 7-10. Inspection of `addTo10.ts` confirmed the bias was real:

The original algorithm picked `a` uniformly from `[0, 10]` then `b` uniformly from `[0, 10 - a]`. This is uniform over `a`, but the marginal distribution over sums is heavily right-weighted: sum=10 has 11 valid pairs (0+10, 1+9, ... 10+0), sum=0 has only one (0+0). Combined with uniform `a`, the result is:

| Sum | P(sum) | Bias |
|---|---|---|
| 0 | ~0.8% | (way under-represented) |
| 5 | ~6.7% | |
| 9 | ~18.4% | (over-represented) |
| 10 | ~27.5% | (severely over-represented) |

Sum 0-6 appears ~30% of the time; sum 7-10 appears ~70%. Pedagogically wrong for an "exposure to all answer values" learning goal.

The original doc comment in `addTo10.ts` actually anticipated this: *"Acceptable for v1; if pedagogy ever requires uniform-pair distribution, swap in a rejection-sample or precomputed pair table."* Story 7 is the swap.

**Why uniform-over-sums (not uniform-over-pairs):**

Two correctness-equivalent approaches were considered:

- **Option A (chosen): pick sum first, then `a`.** Uniform distribution over the ANSWER. Sum=0 (only `0+0`) appears as often as sum=10 (any of 11 pairs).
- Option B: rejection-sample pairs `(a, b)` uniformly with constraint `a+b ≤ 10`. Uniform over pairs — but same right-skew over sums as the old algorithm (since high sums have more valid pairs).

For mathBasher's learning goal — give kids equal exposure to every answer value — option A is correct. Option B would just preserve the original bias under a different name.

**Side note on the broader generator family:**

When add-to-20 / subtract-to-10 / subtract-to-20 generators land (planned in sprints 1.1-1.3), they should follow the same uniform-over-answer pattern. Worth flagging in their stories at planning time so the bias doesn't get re-introduced.

## Out of scope

- **Curation of the sprite pool.** All 45 spritesheets get loaded in this sprint. Picking the keepers is sprint 0.7 Story 4.
- **Tier-aware curation** (different keepers per tier) — only one shared pool, even if some sprites look better at one tier than the other.
- **Per-sprite tuning** (one sprite shown larger than another, or one with a special effect). All sprites use the same display-size logic.
- **Hero sprite re-skin.** The hero is still the yellow block in 0.6.3 — sprint 0.7 Story 3 is when the hero gets a real sprite.
- **Particles, screen shake, etc.** — sprint 0.7 Stories 6–8.

## Why this is a separate sprint and not "fold into 0.7"

Three reasons:

1. **Validation-before-investment.** Field-testing sprite-on-block animation against the actual gameplay loop catches problems (stuttering, occlusion, motion sickness, "looks good static, looks bad in motion") that a static preview can't surface. Better to find them before committing to ~50 final-keeper sprites in 0.7.
2. **Tuning isolation.** The shooter-speed and jiggle tweaks are gameplay-feel changes that benefit from being playtested in isolation. Bundling them with the bigger Kenney-pack art swap in 0.7 makes diagnosing "did the new feel break something or did the new art" harder.
3. **Sprint 0.7 stays focused.** 0.7 has 8 stories already (asset sourcing, BootScene loader, hero re-skin, alien re-skin, projectile re-skin, particles, screen shake, audio hooks). Adding three more inflates risk of the sprint over-running.

## What ships when this closes

- Animated sprite-on-block in production gameplay (random pick per block, both tiers).
- Faster shooter movement (+15%).
- 1-second pre-fall jiggle on every question.
- Plus whatever asset registry / boot wiring fell out of Story 1.

The 90 untracked spritesheet candidates in `public/assets/sprites/aliens/{128,192}/` graduate from "QA pool" to "actively used during play" — they're loaded and rendered for real. They may or may not be the FINAL keepers (sprint 0.7 still picks the keepers), but the wiring proves out.
