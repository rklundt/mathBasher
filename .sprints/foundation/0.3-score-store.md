# Sprint 0.3: Score Store and Scoring

**Phase:** Foundation
**Status:** Closed
**Closed:** 2026-05-09
**Blocks:** 0.5 Gameplay core
**Depends on:** 0.1 Scaffold
**Estimated effort:** 0.5 day (actual: ~0.5 day plus a small wrap-fix touchup)

## Summary

Build the scoring math and the high-score interface. Defines `IScoreStore`, ships an in-memory `SessionScoreStore` (high scores reset on page reload, by design for v1), and ships a `ScoreCalculator` that turns per-question outcomes into a final score per the config formulas. All pure TypeScript, fully unit-tested. The interface design must let a future `ApiScoreStore` drop in with no changes to game code.

## Stories

### Story 1: Score store interface

**Type:** Code/data definition
**Output:** `src/services/IScoreStore.ts`
**Acceptance:**
- Exports:
  ```ts
  export interface ScoreEntry {
    gameId: string;        // 'alien-shoot'
    mathId: MathId;
    speed: SpeedKey;
    score: number;         // points
    correctCount: number;  // 0..questionsPerRound
    passed: boolean;
    achievedAt: number;    // epoch ms
  }

  export interface IScoreStore {
    save(entry: ScoreEntry): Promise<void>;
    top(filter: { gameId: string; mathId: MathId; speed: SpeedKey }, n: number): Promise<ScoreEntry[]>;
    bestForCombo(filter: { gameId: string; mathId: MathId; speed: SpeedKey }): Promise<ScoreEntry | null>;
  }
  ```
- All methods are async-shaped even for the in-memory implementation, so the API never changes when the store moves to a backend

### Story 2: Session score store

**Type:** Code
**Output:** `src/services/SessionScoreStore.ts`
**Acceptance:**
- In-memory implementation of `IScoreStore`
- Stores all entries in a `ScoreEntry[]` field
- `top()` returns sorted by `score` descending, sliced to `n`, filtered by combo
- `bestForCombo()` returns highest-score entry for that combo, or `null`
- No localStorage. No persistence. Clears on page reload. (Persistence is a later sprint, intentionally.)
- Logs each `save` and `top` call via `_th` (Information severity, props: `gameId`, `mathId`, `speed`, on save also `score`)

### Story 3: Score calculator

**Type:** Code
**Output:** `src/services/ScoreCalculator.ts`
**Acceptance:**
Exports:
```ts
export interface QuestionOutcome {
  wasCorrect: boolean;
  usedWrongShot: boolean;   // did the player fire wrong before getting it right?
}

export class ScoreCalculator {
  constructor(mathId: MathId, speed: SpeedKey);
  recordOutcome(outcome: QuestionOutcome): void;
  get score(): number;
  get correctCount(): number;
  get passed(): boolean;       // correctCount >= config.round.passingCorrect
  get stars(): 0 | 1 | 2 | 3;  // based on config.round.starThresholds
}
```

Behavior:
- `recordOutcome({ wasCorrect: true, usedWrongShot: false })` adds `config.scoring.basePerCorrect * mathMult * speedMult`
- `recordOutcome({ wasCorrect: true, usedWrongShot: true })` adds `config.scoring.basePerCorrect * mathMult * speedMult * config.scoring.afterWrongShotMultiplier`
- `recordOutcome({ wasCorrect: false, ... })` adds 0 (timeout or never hit right)
- All math multipliers come from `config`; the calculator does NOT hard-code numbers

### Story 5: Unit tests

**Type:** Test
**Output:** `src/services/SessionScoreStore.test.ts`, `src/services/ScoreCalculator.test.ts`
**Acceptance:** Tests pass via `pnpm test`. Coverage of:

`SessionScoreStore`:
- `save` then `top(filter, 3)` returns entries sorted descending by score
- `top` filters by combo (does not mix mathIds or speeds)
- `bestForCombo` returns the highest-score entry, or `null` if none

`ScoreCalculator`:
- 20 correct, no wrong shots, on Add-to-10 / Medium = `20 * 100 * 1.0 * 1.25 = 2500`
- All outcomes wrong = score `0`, correctCount `0`, `passed: false`, `stars: 0`
- 14 correct of 20 = `passed: true`, `stars: 1`
- 17 correct of 20 = `stars: 2`
- 19 correct of 20 = `stars: 3`
- A correct after wrong-shot adds `basePerCorrect * mathMult * speedMult * 0.5`
- All numeric assertions read multipliers from `config`, not hard-coded — so tuning the config doesn't break these tests

## Notes for Claude Code

- Async signatures on `IScoreStore` are deliberate even though in-memory is sync. Don't "simplify" to sync. The whole point is that API store will be a drop-in.
- Don't add localStorage in this sprint. Persistence (across page reloads, even without an account) is a deliberate post-MVP decision.
- The `ScoreCalculator` is simple enough that you may be tempted to inline the math in `GameScene`. Don't. The whole reason it's a class is to make the scoring rules unit-testable and to keep gameplay code thin.
