## Summary

mathBasher is deploying to **Azure Static Web Apps** (decided 2026-05-22). The game is a 100 % static Vite SPA — no backend needed for gameplay — so SWA is the cheapest + simplest fit. The Express server (`/server/`) stays in the repo unbuilt-for-deploy so a future "mature to App Service" move is a deployment-target swap, not a rewrite.

This sprint absorbs the **Phaser-chunk CDN cache-header story** — formerly sprint 2.2.1 Story 13, which was BLOCKED there because cache headers needed a deployment target to exist. On Static Web Apps the cache policy is just a committed `staticwebapp.config.json` file, so the work is **no longer blocked** — it lands here alongside the deploy.

## Deployment decisions (settled 2026-05-22)

Settled in a planning discussion before the sprint opened — the build stories below assume these:

- **Hosting:** Azure Static Web Apps, **Free plan** (supports up to 3 staging environments).
- **SWA wiring:** the SWA resource was created with deployment source = **"Other"** — NOT the portal's GitHub auto-connect. The GitHub Actions workflow is **hand-authored**, not wizard-generated. This keeps it a clean, sprint-tracked deliverable with explicit pnpm handling, instead of a random-named file the wizard commits straight to `main`.
- **Deployment token:** stored as the GitHub Actions secret `AZURE_STATIC_WEB_APPS_API_TOKEN` (added by the project owner). Never committed.
- **Dual-environment branching model (Option A):**
  - A new `development` branch, created from `main`.
  - Sprint branches → PR → **`development`** → auto-deploys to a named **`development`** SWA staging environment (stable pre-prod URL).
  - A separate **`development` → `main`** PR is the deliberate "ship to production" gate → auto-deploys to the SWA **production** environment.
  - `main` is the production branch; only ever updated via that promotion PR.
  - Deploys are **push-triggered only** (on `development` and `main`) — no per-PR preview environments — so exactly two SWA environments are in use, comfortably inside the Free plan's limit of 3.
- **pnpm build:** the workflow builds with pnpm explicitly (`pnpm install --frozen-lockfile` + a Vite-only build). SWA's Oryx auto-build is bypassed (`skip_app_build`) because it is unreliable at detecting pnpm.
- **Docs split:** the non-sensitive deploy flow gets a short note in the committed `DeveloperGuide.md`; the full operational runbook (environment URLs, token rotation, rollback click-paths) lives in a **gitignored** `docs/deployment-runbook.md` — kept out of the public repo per the project owner's preference.

(This supersedes the App-Service-based plan in the older sprint 3.5; retiring or re-scoping 3.5 is handled in this sprint's audit story.)

## Stories

### Story 1: `staticwebapp.config.json` — cache headers, SPA routing, security headers

**Type:** Code (config)

**Status:** ✅ Shipped (commit `d914819`). `public/staticwebapp.config.json` created — tiered caching (immutable for Vite's content-hashed bundles, 7-day `max-age` for stable-named game content under `/assets/{sprites,audio,images}`, `no-cache` for `index.html`), SPA `navigationFallback`, security headers, explicit `.webp` MIME. A full CSP was deferred — it needs testing against Phaser's canvas / WebAudio first. Header behaviour is verified against the live site in Story 3.

**Context:** The Phaser vendor-chunk split shipped in sprint 2.2 (`vite.config.ts` `manualChunks` → `phaser-<hash>.js` + `index-<hash>.js`). The caching payoff only lands if the host serves hashed assets with long-lived immutable cache headers. On Azure Static Web Apps that is a committed `staticwebapp.config.json`.

**Output:**
- New `staticwebapp.config.json` placed in **`public/`** (so Vite copies it into `dist/` — SWA reads the file from the deployed output root, not the repo root).
  - Hashed build assets (`/assets/*`) → `Cache-Control: public, max-age=31536000, immutable`.
  - `index.html` → `Cache-Control: no-cache` (un-hashed entry point — must re-fetch to pick up new asset hashes).
  - `navigationFallback` → `index.html`, with `/assets/*` excluded so a genuinely missing asset still 404s honestly.
  - MIME-type correctness for `.webp` if SWA does not serve it right by default (verify).
  - Basic security headers: `X-Content-Type-Options: nosniff`, a `Referrer-Policy`, and frame protection. A full Content-Security-Policy is a judgment call — add it only if it does not break Phaser's canvas / WebAudio / blob usage; otherwise note it as deferred to a follow-up.

**Acceptance:**
- Hashed assets served `immutable`; `index.html` served `no-cache`.
- A returning visit reuses the cached `phaser-*.js` (DevTools Network → "(disk cache)").
- Deep-link / refresh on any path serves the app, not a 404.
- Security headers present on the response.

### Story 2: Deployment pipeline — `development` branch + hand-authored GitHub Actions workflow

**Type:** Code (CI/CD) + repo config

**Status:** ✅ Shipped. `development` branch created at kickoff. **No new build script needed** — the existing `build:client` script (`tsc -p tsconfig.app.json --noEmit && vite build`) already does the Vite-only build, skipping the server `tsc`. `.github/workflows/deploy.yml` hand-authored: push-triggered on `main` + `development`; pnpm 9 + Node 20; `install --frozen-lockfile` → `build:client` → `test` (a test gate, added so a build that fails typecheck or tests never deploys) → `Azure/static-web-apps-deploy@v1` with `skip_app_build`. `deployment_environment` resolves to `development` on the dev branch, empty (production) on `main`. A `concurrency` group makes the latest push supersede an in-flight run. First-deploy verification is Story 3.

**Context:** Encodes the dual-environment branching model (Option A above). Hand-authored, pnpm-explicit, push-triggered.

**Output:**
- Create the `development` branch from `main` (identical content) so the staging environment has something to deploy.
- Build script: **no new script needed** — the existing `build:client` script does the Vite-only build (app typecheck + `vite build`), skipping the server `tsc` that the default `build` script also runs.
- Hand-author `.github/workflows/deploy.yml` (plain-English name):
  - Triggers on `push` to `main` and `development` only (no `pull_request` trigger → no per-PR preview environments).
  - Sets up pnpm 9 + Node 20, runs `pnpm install --frozen-lockfile`, `pnpm build:client`, then `pnpm test` as a deploy gate.
  - Deploys via `Azure/static-web-apps-deploy@v1` with `skip_app_build: true`, the built `dist/` as the app artifact, and the `AZURE_STATIC_WEB_APPS_API_TOKEN` secret.
  - Push to `development` → `deployment_environment: development` (named SWA staging env, stable URL).
  - Push to `main` → production environment (no `deployment_environment`).
- No secrets, no tooling-context / sprint references in the workflow file; plain-English job + workflow names.

**Acceptance:**
- `development` branch exists on `origin`.
- `pnpm build:client` produces `dist/` without running the server `tsc`.
- The workflow file is committed, references only the `AZURE_STATIC_WEB_APPS_API_TOKEN` secret, contains no leaked internal vocabulary, and is valid YAML GitHub accepts.

- Document the production **cache model** in `DeveloperGuide.md`: the two tiers (immutable content-hashed bundles vs. 7-day stable-named game content) and the **convention that a changed game asset must get a new filename** — stable-named assets are cached 7 days, so a rename is what makes a content change propagate instantly (the same effect Vite's hashing gives the code bundles). A `Ctrl+Shift+R` only busts the cache for the one developer doing it, so it is not a release mechanism.

**Acceptance:**
- `docs/deployment-runbook.md` exists locally, is gitignored, and is NOT tracked by git.
- `DeveloperGuide.md` documents the deploy + rollback flow at a non-sensitive level.
- `DeveloperGuide.md` documents the cache model + the changed-asset-rename convention.
