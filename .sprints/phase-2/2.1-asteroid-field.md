## Summary

Adds the **second** game mode to mathBasher. "Pick a Game" screen currently shows "Alien Shoot" (the lane-drop gameplay shipped through Phase 1) + a disabled "Coming soon" tile. This sprint replaces the disabled tile with **"Asteroid Field"** — a free-aim, free-position gameplay variant that reuses all the math content from Phase 1.

**Core gameplay difference vs Alien Shoot:**

| | Alien Shoot | Asteroid Field |
|---|---|---|
| Answer positioning | 4 fixed lanes, drop straight down | 4 floating positions, drift in 2D |
| Hero movement | Auto side-to-side between bounds | Static center; ROTATES to aim |
| Fire direction | Straight up from hero | In the aimed direction |
| Win condition | Shoot the lane with correct answer | Shoot the asteroid with correct answer |
| Cognitive load | Math + lane-timing | Math + aim coordination |

**What stays exactly the same** (architecture win):
- All 9 math generators (add-to-10/20, sub-to-10/20, mult-to-100/144, div-to-100/144, mixed)
- ScoreCalculator (reads mathId + speed from Settings)
- HudScene (math prompt, score, dots, mute, pause — all generic; no changes)
- Round structure (20 questions, 14 to pass, star thresholds, anti-repeat sliding window)
- Pause overlay, settings, telemetry event names, attribution footer
- Speed selector on DifficultyScene (Slow/Medium/Fast)
- Anti-repeat sliding window (per-round prompt history — game-mode-agnostic)

**Important architectural call: extract a base class or composition pattern?** GameScene currently is monolithic for Alien Shoot. Asteroid Field needs much of the same lifecycle (mathId/speed init, scoreCalculator wiring, question loop, HUD events) but a different render-and-input loop. Decision deferred to Story 1 — likely a `BaseGameScene` abstract class OR a `GameRoundController` helper that both scenes use. Will surface options in chat once I scope the actual shared surface.

## Stories

### Story 1: Refactor — extract shared game-scene lifecycle

**Type:** Code (architectural prep — required before the second scene)

**Output:**
- A shared abstraction that holds the parts of GameScene that aren't Alien-specific:
  - mathId/speed init from Settings
  - ScoreCalculator construction
  - Question loop (`startNextQuestion`, `afterQuestion`, anti-repeat sliding window, `endRound`)
  - Event emission (`questionStarted`, `questionEnded`, `correctHit`)
  - Pause/resume hooks
  - HUD launch
- AlienShootScene becomes the old GameScene minus the shared bits
- Asteroid Field scene (Story 2) consumes the same abstraction

**Approach (decide at implementation time):**
- **Option A: `BaseGameScene` abstract class** — both scenes extend it. Pros: TypeScript enforces hooks. Cons: Phaser scenes don't love deep inheritance; multi-level scene classes can be fiddly.
- **Option B: `GameRoundController` composition helper** — a plain class that takes a scene reference and orchestrates the round loop. Pros: testable in isolation; no inheritance fragility. Cons: more wiring per scene.
- **Option C: just duplicate** — two near-identical scenes. Pros: simple. Cons: drift, anti-DRY.

Recommend B unless implementation surfaces a reason otherwise. Will commit to a path in the first implementation pass and surface the call in chat before locking in.

**Acceptance:**
- Alien Shoot still works identically (same score, same events, same timing) — verified by manual playtest
- The shared abstraction is consumed by both scenes via the same call shape
- `pnpm typecheck` / `pnpm test` green; existing 249 tests still pass

### Story 2: AsteroidFieldScene — new scene

**Type:** Code (the bulk of the sprint)

**Output:** `src/game/scenes/AsteroidFieldScene.ts` (registered in main.ts; routed from GameSelectScene when player picks "Asteroid Field")

**Gameplay loop per question:**
1. Question starts: 4 asteroids spawn at random positions on the playfield, each carrying one of the 4 candidate answers
2. Asteroids drift slowly in random 2D directions (gentle, predictable speeds — not chaotic)
3. Hero sits centered on the playfield, rotates to aim (touch/mouse/keyboard input)
4. Player fires; projectile travels in aimed direction
5. Hit an asteroid: correct → next question, wrong → wrong-shot penalty (asteroids speed up briefly, same pattern as Alien Shoot)
6. Asteroids that drift off-screen wrap around (or get gently bounced back — design call)

**Physics design (initial values; tune in playtest):**
- 4 asteroids spawned at random positions on a 1280×720 canvas, with min-distance from each other so they don't immediately overlap
- Drift speeds (per speed setting):
  - Slow: 30 px/s, gentle directions
  - Medium: 50 px/s
  - Fast: 75 px/s
- Asteroid wrap behavior: edge-wrap (off the left side → appear on the right). Keeps them in play indefinitely so the question never times out via off-screen drift.
- No timeout per question (vs Alien Shoot's "alien-reaches-hero" timeout). Asteroid Field is a pure-aim-skill mode; if you can't aim, you can't win — but you can take your time. Could revisit with a per-question time limit later if playtest shows kids park forever.

### Story 3: Hero ship — rotating + aiming

**Type:** Code

**Output:** New `AsteroidHero` entity in `src/game/entities/` (or reuse existing Hero with a "rotates" mode — TBD per refactor choice)

**Mechanics:**
- Hero ship sits centered on the playfield (x = canvas-center, y = canvas-center)
- Rotates to face the cursor / touch position / keyboard arrows
- Fires projectile in the facing direction on tap/click/Space
- Uses the same sprite assets as the Alien Shoot hero (round-robin speeder-1/2/3 from sprint 0.7)
- Engine glow particle effect points "backward" relative to facing (vs always-downward in Alien Shoot)

**Input model decisions** (need user input):
- **Phone (touch):** Tap anywhere on the screen → hero rotates to face the tap + fires? OR tap to rotate, tap-again to fire? (Recommend tap = fire-toward-tap-location for simplicity)
- **Desktop (mouse):** Mouse position drives rotation continuously; click or Space fires?
- **Keyboard-only:** Arrow keys rotate, Space fires?

Default suggestion: tap-to-fire-toward-tap on mobile; mouse-aim + click/Space on desktop; arrow-rotate + Space on keyboard.

## Open design questions (need user input before coding)

1. **Input model on phone**: tap-to-fire-toward-tap, OR tap-to-rotate + double-tap-to-fire? Recommend the former (simpler).
2. **Per-question timeout**: NONE (player can take as long as they want), OR a generous countdown (e.g. 30s) for the round to feel paced? Recommend NONE for v1 — Asteroid Field is more skill than time pressure.
3. **Asteroid drift physics**: straight-line drift with edge-wrap, OR bouncing-off-walls, OR slow-orbit? Recommend straight-line + edge-wrap (simplest, predictable for kids).
4. **Art direction**: kid-friendly cartoon asteroids (recommend) vs realistic space rocks vs glowing crystals?
5. **Story 1 refactor approach**: A (base class), B (composition helper), C (duplicate). Recommend B.
