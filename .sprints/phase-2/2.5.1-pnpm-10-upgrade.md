## Versioning note (read first)

This is a **toolchain-only** change: no runtime/app code is touched, and with the dependency overrides held (vite `^6.4.2`, esbuild `^0.25.0`) the built `dist/` is functionally identical. Therefore **`package.json` `version` stays at `2.5.0`** — the shipped artifact doesn't change, so the app version shouldn't either. "2.5.1" is the SPRINT-TRACKING label only (a maintenance half-step between the 2.5.0 release and the 2.5.2 visual-tweaks / 2.5.3 splash feature sprints). VERSIONS.md gets a short **tooling note** under the current version rather than a new app-version heading.

## Problem

Running `pnpm dev` (or any pnpm command) in this repo currently prints:

```
[WARN] The "pnpm" field in package.json is no longer read by pnpm. The following
keys were ignored: "pnpm.overrides", "pnpm.onlyBuiltDependencies".
See https://pnpm.io/settings for the new home of each setting.
```

Investigation (2026-05-23):
- Effective pnpm is **9.15.0** (pinned via `package.json` `packageManager: pnpm@9.15.0`; corepack 0.34.6 present; two global pnpm binaries on PATH — `C:\nvm4w\nodejs\pnpm` and `C:\Users\Ray\AppData\Roaming\npm\pnpm`).
- pnpm 9.15.0 emits the forward-looking deprecation warning **but does not yet fully support** the new settings location: creating a settings-only `pnpm-workspace.yaml` on 9.15.0 fails with `ERROR packages field missing or empty`. The actual relocation of `overrides` / `onlyBuiltDependencies` into `pnpm-workspace.yaml` is a **pnpm 10** feature.
- The overrides are **load-bearing and currently applied**: `pnpm-lock.yaml` resolves `esbuild@0.25.12` (the 0.25.x dev-server security fix) and `vite@6.4.2`. Dropping the `pnpm` field WITHOUT relocating would risk regressing the esbuild security floor on a future install.

So the clean fix is **upgrade to pnpm 10** and migrate the settings to `pnpm-workspace.yaml` (which 10 supports properly), regenerating the lockfile.

## Key risk — CI auto-picks-up the pnpm version

`.github/workflows/deploy.yml` uses `pnpm/action-setup@v4` with **no pinned `version:`**, so it reads the pnpm version from `package.json` `packageManager`. Bumping `packageManager` to `pnpm@10.x` means **CI uses pnpm 10 on the next deploy**, and its `pnpm install --frozen-lockfile` step will **FAIL unless the lockfile is regenerated by pnpm 10 and committed**. The PR's green CI run is therefore the real proof the upgrade works end-to-end.

## Stories

### Story 1: Upgrade pnpm + relocate settings + regen lockfile

**Type:** Toolchain (config + lockfile)

**Spec:**
- Pick a specific recent stable **pnpm 10.x** (pin an exact patch, not a range).
- `corepack use pnpm@10.<x>` (drives both the `packageManager` field bump AND the running binary so they stay in sync; work through any shim friction with the two global installs).
- Create `pnpm-workspace.yaml` with the two relocated settings (single-package repo — settings only, no `packages:` globs intended, but pnpm 10's requirement here must be confirmed during implementation; if 10 still demands a `packages:` key, add `packages: ['.']` or the minimal form pnpm 10 accepts):
  ```yaml
  overrides:
    vite: ^6.4.2
    esbuild: ^0.25.0
  onlyBuiltDependencies:
    - ffmpeg-static
    - sharp
  ```
- Remove the `pnpm` field from `package.json` (lines for `overrides` + `onlyBuiltDependencies`). LEAVE the `engines.pnpm` constraint — but bump it from `>=9.0.0` to `>=10.0.0` to match the new floor.
- `pnpm install` to regenerate `pnpm-lock.yaml` under pnpm 10. Confirm the overrides still resolve (esbuild stays `0.25.x`, vite stays `6.4.x`) — diff the lockfile and eyeball that no critical pin moved DOWN.
- `.npmrc` settings (`node-linker=hoisted`, `store-dir=.pnpm-store`, `prefer-frozen-lockfile=true`) carry over to pnpm 10 unchanged — confirm they're still honored.

**Output:**
- `package.json` — `packageManager: pnpm@10.<x>`, `engines.pnpm: >=10.0.0`, `pnpm` field removed.
- `pnpm-workspace.yaml` — new, holding the two relocated settings.
- `pnpm-lock.yaml` — regenerated by pnpm 10.
- `version` UNCHANGED at `2.5.0`.

**Acceptance:**
- `pnpm dev` / `pnpm install` print NO settings-relocation warning.
- Overrides still applied (esbuild 0.25.x, vite 6.4.x in the lockfile).
- `pnpm typecheck`, `pnpm test`, `pnpm build` all green locally.

### Story 2: CI verification + close

**Type:** Validation

**Spec:**
- Push the branch + open the PR to `development`. The CI deploy workflow runs `pnpm install --frozen-lockfile` under pnpm 10 (auto-selected from the bumped `packageManager`). **CI must go green** — this is the load-bearing proof the regenerated lockfile + pnpm 10 work in the clean-room CI environment.
- If CI's frozen-lockfile install fails, the lockfile regen didn't capture something — fix locally + re-push, don't merge red.
- VERSIONS.md: add a short tooling note under the current `[2.5.0]` (or a dedicated `[2.5.0] tooling` sub-note) — NOT a new app-version heading. State: "Dev toolchain upgraded pnpm 9.15 → 10.x; overrides + onlyBuiltDependencies relocated to pnpm-workspace.yaml; no app/runtime change."
- Light audit only (no six-reviewer pass needed — toolchain change, no app surface). DevOps reviewer optional if a sanity check on the CI workflow interaction is wanted.

**Acceptance:**
- PR CI is green (frozen-lockfile install + typecheck + test + build under pnpm 10).
- No app version bump.
- VERSIONS.md tooling note added.
