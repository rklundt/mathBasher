# Sprint 2.1.8: Loading-bar visibility (boot + per-game scene)

**Phase:** 2
**Status:** Closed
**Closed:** 2026-05-17
**Released:** 2026-05-17 (v2.1.8)
**Blocks:** none (2.2 Number Climb depends on the loading-pattern this sprint cleans up, so it should land first)
**Depends on:** 2.1.6 (lazy per-game asset loading) — closed 2026-05-17 (v2.1.6). 2.1.7 deliberately skipped so the version line can leave room for hotfixes inside 2.1.6's footprint if they appear.
**Estimated effort:** half-day. Two narrow stories + 6-reviewer audit + close.

## Summary

Sprint 2.1.6 partitioned assets into scopes and added per-game preloads. Playtest of v2.1.6 surfaced two real UX issues — both about VISIBILITY between user-tap and on-screen-content, not actual load time:

1. **Splash → menu gap has no loading affordance.** The "Tap to play" splash dismisses immediately on click; Phaser then constructs + runs `BootScene.preload` to load ~2 MB of eager assets; THEN the menu appears. Between the tap and the menu, the kid sees either a blank canvas or the splash mid-fade with no progress indicator. On a slow phone this reads as "did my tap register? did the app crash?" The Phaser-based loading bar inside `BootScene.preload` doesn't fully cover the gap because (a) the Phaser canvas hasn't painted its first frame yet during the construction delay, and (b) at ~2 MB the actual load completes in well under a second so even when the bar appears it may flash. We need a loading affordance that's visible IMMEDIATELY post-tap and stays up through both the Phaser construction AND the boot preload.

2. **First-time per-game loads appear to hang.** The LoadingOverlay attached in `AsteroidFieldScene.preload()` / `GameScene.preload()` doesn't render visibly during the scene transition. Suspected cause: Phaser's scene-transition timing means the new scene's preload-time GameObjects aren't on-screen until `create()` runs (at which point the load is already done). The kid sees DifficultyScene → ~1-2 seconds of apparent freeze → game suddenly running. Reads as a hang.

Both fixes are about PERCEPTION, not bytes-on-the-wire. The asset loads are already fast; the user just can't see that work is happening.

## Stories

### Story 1: Splash → menu transition loading bar (DOM, not Phaser)

**Type:** Code

**Problem framing:** The Phaser-based `LoadingOverlay` inside `BootScene.preload` can't bridge the splash-dismiss → menu-appears gap because Phaser hasn't painted its first frame yet during the construction delay. The bar needs to live IN THE DOM (index.html / splash markup), not in Phaser, so it can render the instant the user taps.

**Output:**
- `index.html` splash markup gains a hidden-by-default loading-bar section (label + thin progress bar, CSS-styled to match the existing splash palette `#1f2740` / `#fbbf24`).
- On "Tap to play" click, the splash content morphs in place: the title + subtitle stay; the "Tap to play" button is replaced (display:none) with the loading bar (display:flex). This gives instant visual feedback to the tap.
- The loading bar reflects Phaser's actual progress. Wire the existing Phaser loader's `progress` event in `BootScene.preload` to drive the DOM bar's width. Once Phaser fires the `complete` event, the splash dismisses entirely (existing `splash.classList.add('hidden')` call moves from `boot.ts` to a `BootScene.create` callback so it fires AFTER the load + animation rather than before construction).
- The Phaser-side `attachLoadingOverlay` call in `BootScene.preload` is REMOVED (splash bar replaces it). One bar, one place, no double-render.
- Add a `minDisplayMs` floor (e.g. 500ms) on the splash bar so a sub-second load still shows the bar for a beat — the kid sees the bar appear, fill, and dismiss cleanly even on a fast network. Implementation: a `setTimeout` race; the splash hides on `max(loadComplete, minDisplayMs)`.

**Why DOM, not Phaser:** the bar must be visible BEFORE Phaser's first frame paints. Only the DOM splash overlay is up at that moment. Same reasoning as why the splash itself is HTML/CSS — sprint 0.5.4's whole point.

**Acceptance:**
- Tap "Tap to play" → loading bar appears within ~50ms (DOM paint, no Phaser).
- Bar fills smoothly as Phaser preloads the ~2 MB boot bundle.
- Bar stays visible for at least 500ms regardless of network speed.
- Bar dismisses cleanly → menu appears (no blank-canvas flash between).
- `pnpm typecheck` / `pnpm test` / `pnpm build` green.

### Story 2: Per-game scene-transition loading bar

**Type:** Code (the meatier piece)

**Output:** Pick whichever of these approaches works in playtest — Architect/Senior Dev review will lock the choice:

**Option A: defer the scene.start until assets are ready.** DifficultyScene (the scene that calls `scene.start(GameSceneKey)`) takes responsibility for kicking off the load + showing a loading bar IN ITSELF, then transitioning once the bar completes. The game scenes' `preload()` becomes a no-op (or just keeps the idempotent `loadGameBundle` call as a safety net for direct entries).

**Option B: dedicated `LoadingScene` between DifficultyScene and the game scene.** DifficultyScene starts LoadingScene with `{ targetScene: AsteroidFieldScene.key }`. LoadingScene runs the bundle load + shows the bar, then `scene.start(targetScene)` once done. Standard Phaser pattern. Costs: one more scene to wire (sceneKeys, app/boot.ts, etc.). Benefits: clean separation; reusable for future game modes.

**Option C: figure out why the preload-time loading bar isn't rendering** and fix the render-timing issue directly. Risks: Phaser-internal — might end up depending on undocumented frame timing.

**Recommended: Option B.** It's the standard Phaser pattern for exactly this situation, doesn't require restructuring DifficultyScene's flow, and the cost (one new scene + 4-5 lines of glue) is small. Confirm in chat before coding.

**Acceptance:**
- First pick of either game mode shows a visible loading bar with progress, ~1-2 seconds (matches the actual lazy-load duration).
- Subsequent picks of the same mode are instant (Phaser cache means `totalToLoad === 0`; LoadingScene either short-circuits to instant transition OR shows the bar at 100% for the same `minDisplayMs` floor for visual consistency — pick one in playtest).
- Quit-to-menu + re-enter the same game mode → instant (cache hit).
- Quit-to-menu + enter the OTHER game mode → loading bar appears (cold load for that mode).

## Notes for Claude Code

- The actual asset loading is fine — sprint 2.1.6 verified the boot drop from ~5.5 MB → ~2 MB and the per-game lazy-load. This sprint is purely VISIBILITY / PERCEPTION, not bytes-on-the-wire.
- Be careful with the `minDisplayMs` floor at boot — don't extend the boot to feel slower than it is. 800ms is short enough that "the bar appeared and finished" reads as snappy, not laggy.
- LoadingScene (if chosen) needs an SPDX header + a comment explaining it sits between DifficultyScene and the target game scene as a load-progress intermediate.
- If `LoadingScene` is added, register it in `src/app/boot.ts` AFTER BackgroundScene + AttributionScene so the bg shows through and the AttributionScene footer overlays correctly.
