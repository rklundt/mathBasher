## Summary

Two new math types — **"Add Fractions"** and **"Subtract Fractions"** — available in all three game modes. They are the project's first generators that break two long-standing assumptions, which is why they earn their own sprint rather than a story in 2.2.1:

1. **Non-integer answers.** Every existing generator produces integer answers and the whole stack assumes it — `Question.correctAnswer: number`, `Question.choices: number[]`, and the answer-rendering in all three games shows the bare number. A fraction answer (`3/8`, `1 1/2`, `4`) cannot ship as a bare `number`; `0.375` is wrong for a kids' math game. The answer needs a display representation.
2. **Difficulty-varying content.** Both types change their question CONTENT based on the Easy/Medium/Hard (Speed) selector. No existing generator does this — generators are speed-agnostic today; speed only affects game pace + score multiplier.

Add and Subtract Fractions share all the infrastructure (the `Question` display layer, speed-aware plumbing, cross-game fraction rendering, wiring); only the two generators differ. The Subtract generator adds one constraint the Add generator doesn't have — the result must be non-negative.

The three difficulty bands (driven by the Speed selector), mirrored across both types:
- **Easy** — LIKE fractions (same denominator). Denominator 1-12. Add: `2/5 + 1/5 = 3/5`. Subtract: `4/5 − 1/5 = 3/5`.
- **Medium** — like fractions WITH whole numbers (mixed numbers). Add: `1 1/2 + 2 1/2 = 4`. Subtract: `3 3/4 − 1 1/4 = 2 1/2`.
- **Hard** — UNLIKE fractions (different denominators). The larger denominator is 2× or 3× the smaller (no more); the smaller denominator is 1-4 — so the maximum denominator is 12 (3 × 4). Add: `1/4 + 1/8 = 3/8`. Subtract: `3/4 − 1/8 = 5/8`.

### Story 1: Fraction representation — extend the `Question` type

**Type:** Code (data-layer design — the foundational decision)

**Context:** The central design decision the rest of the sprint builds on. A fraction answer must carry BOTH a numeric value (for equality checks + scoring + distractor math) AND a display string (so `3/8` renders as `3/8`, not `0.375`).

**Output:**
- Extend `Question` (`src/math/types.ts`) with an optional display layer — recommended shape: `correctDisplay?: string` + `choiceDisplays?: string[]` alongside the existing numeric `correctAnswer` / `choices`. When present, rendering uses the display strings; when absent (every existing integer generator), rendering falls back to `String(numericValue)` exactly as today.
- The numeric `correctAnswer` for a fraction is its decimal value (e.g. `3/8` → `0.375`) — used ONLY for internal equality + distractor-distinctness checks, never displayed.
- Document the contract: a generator either supplies display strings for ALL choices or NONE (no partial).

**Acceptance:**
- `Question` carries an optional display layer; all 9 existing integer generators are unaffected (no display strings → unchanged rendering).
- Type-level: a fraction question is well-formed (numeric + display both present + same length).

### Story 3: `addFractions` generator + unit tests

**Type:** Code + tests (the meatiest story)

**Context:** The generator itself — three difficulty bands, fraction arithmetic, reduction, distractors.

**Output:**
- New `src/math/generators/addFractions.ts`. Reads the round speed (Story 2) to pick the band:
  - **Easy** — two like fractions, shared denominator 1-12, sum rendered reduced.
  - **Medium** — two mixed numbers (whole + like fraction); sum may be a whole number (`1 1/2 + 2 1/2 = 4`).
  - **Hard** — two unlike fractions; smaller denominator 1-4, larger denominator = 2× or 3× the smaller (max 12); sum reduced.
- Fraction math helpers: GCD-based reduction (`3/6` → `1/2`), whole-number normalization (`2/2` → `1`, `4/2` → `2`), mixed-number formatting (`3/2` → `1 1/2`).
- Distractor generation producing plausible WRONG fractions — model common kid errors: added the denominators, forgot to reduce, numerator off by one. Distractors must be distinct from each other + the correct answer (both numerically and by display string).
- Unit tests: each band produces valid sums; answers are reduced; denominators obey the rules (Easy 1-12, Hard smaller 1-4 / larger 2-3× / max 12); distractors are distinct + plausible; mixed-number formatting is correct.

**Acceptance:**
- Generator produces correct, reduced fraction sums for all three bands.
- Denominator rules hold across many seeded runs.
- Distractors are distinct + plausible.
- New test file is green; existing tests stay green.

### Story 4: `subtractFractions` generator + unit tests

**Type:** Code + tests

**Context:** The mirror of Story 3 for subtraction. Reuses the SAME shared infrastructure — the `Question` display layer (Story 1), the speed-aware plumbing (Story 2), and the cross-game rendering (Story 5). Only the generator + its wiring entry are new.

**Output:**
- New `src/math/generators/subtractFractions.ts`. Reads the round speed to pick the band, mirroring the Add Fractions difficulty ladder:
  - **Easy** — subtract two like fractions, shared denominator 1-12. e.g. `4/5 − 1/5 = 3/5`.
  - **Medium** — subtract mixed numbers (whole + like fraction). e.g. `3 3/4 − 1 1/4 = 2 1/2`.
  - **Hard** — subtract two unlike fractions; smaller denominator 1-4, larger denominator = 2× or 3× the smaller (max 12). e.g. `3/4 − 1/8 = 5/8`.
- **Non-negative-result constraint** — the key difference from Add Fractions: the minuend must be ≥ the subtrahend so the answer is never negative (a negative fraction is out of scope for the 6-10yo target). The generator picks operands such that `first − second ≥ 0`; for mixed numbers the whole+fraction minuend must be ≥ the subtrahend. A zero result (`2/4 − 1/2 = 0`) is acceptable but should be rare — re-roll if it dominates.
- Reuse the fraction math helpers from Story 3 (GCD reduction, whole-number normalization, mixed-number formatting) — extract them to a shared `src/math/fractionMath.ts` if they aren't already, so both generators import them rather than duplicating.
- Distractor generation for wrong differences — common kid errors: subtracted numerators AND denominators, didn't find a common denominator, off-by-one numerator. Distinct + plausible, same contract as Story 3.
- Unit tests: each band produces valid, non-negative, reduced differences; denominator rules hold; no negative answers across many seeded runs; distractors distinct + plausible.

**Acceptance:**
- Generator produces correct, reduced, **non-negative** fraction differences for all three bands.
- Denominator rules hold; no negative answers across many seeded runs.
- Distractors are distinct + plausible.
- Shared fraction helpers are imported, not duplicated.
- New test file green; existing tests stay green.

### Story 6: Centralize the scoring + difficulty modifier config

**Type:** Refactor (config hygiene — do BEFORE Story 7 so the fraction multipliers land in the centralized home)

**Context:** The numbers that determine score — the per-math-type difficulty multipliers and the per-difficulty (Speed) multipliers — are the most-tuned values in the project and the ones a future contributor most needs to find fast. Today they live in `config.scoring.mathDifficulty` + `config.scoring.speed[*].multiplier`, which is already one file but the "scoring knobs" aren't visually grouped or cross-referenced, and per-game tuning (`config.numberClimb.speed`, `config.asteroidField.speed`) sits elsewhere. This story makes the scoring-modifier surface a single, clearly-labelled, well-documented block so "where do I set the score modifier for a new game / math type" has one obvious answer.

**Output:**
- Consolidate / clearly demarcate the scoring-modifier config in `src/core/config.ts`: a single well-commented `config.scoring` region holding `basePerCorrect`, `mathDifficulty` (per-math-type multipliers), `speed.*.multiplier` (per-difficulty multipliers), and `afterWrongShotMultiplier`. A header comment block documents the formula (`score per correct = basePerCorrect × mathMultiplier × speedMultiplier × wrongShotMult`) and the ladder rationale.
- Where per-game config blocks (`numberClimb`, `asteroidField`) carry difficulty-related tuning, add a one-line cross-reference comment pointing back to `config.scoring` so the relationship is discoverable.
- No behavior change — this is purely a "make the knobs easy to find + change" refactor. Tests stay green by construction.

**Acceptance:**
- All score-determining modifiers are in one clearly-labelled, documented `config.scoring` block.
- Adding a new math type or game mode has one obvious place to set its score modifier.
- No score behavior change; all tests green.

**Type:** Docs + process

**Context:** As the game grows — three game modes, soon 11 math types, three difficulty levels — the scoring picture (what's the max score for game X, math type Y, difficulty Z) is spread across `config.scoring` + per-game `questionsPerRound`. A single reference doc makes the whole scoring surface viewable at a glance, and a CLAUDE.md hook ensures it's kept current as new games / math types land.

**Output:**
- New `docs/SCORING.md` — a reference table of the scoring model:
  - The formula (`score per correct = basePerCorrect × mathMultiplier × speedMultiplier`, round size, max-score derivation).
  - A per-math-type multiplier table (all math types incl. the two new fraction types).
  - A max-score grid: by game mode × difficulty (Easy/Medium/Hard) — noting that all three games share the same max for a given (math type, difficulty) since scoring has no game-mode axis (sprint 2.2.1 story 11).
  - The star-threshold ladder per game.
- Add a line to `CLAUDE.md` (in the scoring/telemetry conventions area) instructing that `docs/SCORING.md` MUST be updated whenever a math type, game mode, or scoring modifier is added or changed — so the doc never goes stale.
- Generated from the config values (cite `config.scoring` as the source of truth) so SCORING.md documents, not duplicates-authoritatively.

**Acceptance:**
- `docs/SCORING.md` exists with the formula, multiplier table, max-score grid, and star ladder.
- `CLAUDE.md` references it as a keep-updated artifact.
