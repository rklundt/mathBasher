## Summary

Two fairness fixes — one per game mode — that both stem from the same observation: today the kid can pass a round without much skill if they brute-force long enough. Climb is OK at the per-floor level but has no overall climb-wide ceiling on mistakes; Asteroid Field has effectively no wrong-shot deterrent at the round level because score-only penalties don't stop a fast clicker from rapid-firing through all the answers.

## Stories

### Story 1: Number Climb — cumulative 3-strike "lives" cap

**Type:** Code (gameplay rule)

**Context:** Climb today allows one mulligan per floor and ends the round on the 2nd wrong on a single floor. There's no climb-wide cap, so a kid who burns one mulligan on every floor reaches floor 12 with no "you've been struggling" feedback. Adding a cumulative cap caps the total ambient sloppiness allowed per climb.

**Spec:**

- Keep the per-floor mulligan rule unchanged (1st wrong on a floor = mulligan with time penalty; 2nd wrong on the same floor = wrong-terminal, round over).
- Add a **cumulative strike counter** across the whole climb. When the counter hits **3**, end the round immediately (same flow as wrong-terminal).
- "Strike" = a mulligan-triggering wrong (the kid had to use their per-floor lifeline). A wrong-terminal also counts as a strike on top of whatever brought the kid there (so a kid who reaches wrong-terminal via a 1st-then-2nd wrong has used 2 strikes that floor).
- HUD surfaces remaining strikes — small icon row (3 hearts / 3 stars / 3 dots) near the timer that empties as strikes are spent. Tooltip or label so a first-time player understands the rule.

**Open question to settle at sprint-start:** does the per-floor wrong-terminal stay (the current rule), or does the cumulative cap replace it (so the kid can burn all 3 strikes on floor 1 and still proceed)? Recommendation: **keep the per-floor terminal AND add the cumulative cap** — strikes accumulate via mulligans across the climb, AND the 2nd wrong on a single floor still ends the round. Most kid-friendly + simplest mental model.

**Output:**

- `NumberClimbScene.ts` — add a `strikesUsed` counter incremented on `handleWrongMulligan` (and on `handleWrongTerminal` — see open question above). When the counter hits the configured ceiling, route to `endRound` with the same "fall off screen" treatment as wrong-terminal.
- `config.numberClimb.maxStrikesPerClimb` = 3 (lifted; future re-tune is a config edit).
- HUD: small remaining-strikes indicator beside the timer.
- Telemetry event: `NumberClimb.strikeBudgetExhausted` at Information severity when the 3rd strike triggers the end.

**Acceptance:**

- 1st mulligan on a floor still works as today.
- 3 cumulative wrongs across the climb → round ends with the wrong-terminal animation.
- HUD shows the remaining strike count.
- Per-floor "2nd wrong = end" rule unchanged (assuming the open question resolves that way).

### Story 2: Asteroid Field — wrong-shot deterrent (rapid-fire fix)

**Type:** Code (gameplay rule)

**Context:** Today the kid can rapid-fire at every asteroid until they hit the correct one and still pass the round. The existing `afterWrongShotMultiplier` (0.5) only reduces the *score*; correctness count (which determines pass/fail) is unaffected. A skilled-clicker kid bypasses the math entirely. Need a deterrent that punishes spam without punishing legitimate accidents (asteroid overlap can put a wrong asteroid in the line of fire even on a fair aim).

**Options recap (project owner discussion, sprint 2.4 review):**

| Option | Mechanism | Trade-off |
|---|---|---|
| A. Strike per round | N total wrong shots = round over | Simple; mirrors Climb. **Concern:** an accidental hit from overlapping asteroids is unfair / feels punishing. |
| B. Per-question shot cap | Max N shots per question; N+1 = question scores 0 | Clear, contained. Feels arbitrary; some orbit setups genuinely need >N shots. |
| **C. Timer reduction per wrong shot** ⭐ | Each wrong shot deducts N seconds from the per-question countdown | Self-balancing — the clock IS the consequence; fair on accidents (lose seconds, not the round); no new UI. **Recommended.** Mirrors Climb's `wrongRungTimePenaltySec`. |
| D. Shot cooldown | Wrong shot = ~1.5s FIRE cooldown | Mechanically prevents rapid-fire. Also slows the next deliberate shot — feels laggy. |
| E. Score multiplier crash | Drop `afterWrongShotMultiplier` from 0.5 → 0 | Minimal change. Doesn't fix the underlying "rapid-fire passes anyway" — only score, not correctness count. |

**Recommendation (project owner): Option C.** Each wrong shot deducts a meaningful chunk (probably 4–6s; tune in playtest) from the per-question countdown. A kid with 1-2 accidental wrong shots still has time. A spammer burns the clock fast and times out (question scores 0). The existing red-timer-color ramp gives visual feedback for free. Conceptually consistent with Climb's wrong-rung time penalty.

**Optionally combine with a soft runaway cap:** if the kid takes more than (e.g.) 6 wrong shots in a single round, end the round early. Defensive only — Option C alone may be enough; settle in playtest.

**Output (if Option C is chosen at sprint-start):**

- `config.asteroidField.wrongShotTimePenaltySec` (probably 5; tune in playtest).
- `AsteroidFieldScene.ts` — on wrong-shot, deduct the configured penalty from the per-question countdown.
- HUD: the timer should visibly *jump* when a wrong shot fires (so the kid registers the penalty — same red-flash treatment Climb uses).
- Telemetry: extend the existing wrong-shot event with `timePenaltySec` for analysis.

**Acceptance:**

- A wrong shot visibly drops the countdown by the configured number of seconds.
- 3-4 rapid wrong shots cause the question to time out (score 0).
- 1-2 accidental wrong shots from asteroid overlap still let the kid finish the question.

### Story 3: New hero sprite — "Space Robot" default with "OG Yellow" fallback

**Type:** Code + assets

**Context:** A new hero image is staged in `.sprite-source/raw/hero/` (project-owner Midjourney output) to refresh the Alien Shoot hero with a more arcade-friendly robot look. The existing speeder set (`speeder-1/2/3`, round-robin per round) should be **preserved as a player-selectable alternative** — the original look isn't lost, and a kid who prefers the old style can opt back in. First time the project lets the player choose a hero in any way; sets the pattern for the sprint 2.5 four-hero diverse picker (which lives in a different story arc).

**Output:**

- Process the new hero source through the sprite pipeline:
  ```
  pnpm sprite:process --kind hero --name space-robot --format webp-lossless .sprite-source/raw/hero/<source>
  ```
  Produces `public/assets/sprites/hero/space-robot.webp`. Lossless WebP per the project's "alpha sprites = lossless" convention (sprint 2.2.1 story 6).
- New `HeroSpriteKeys.SpaceRobot = 'space-robot'` in `src/core/spriteKeys.ts`. Static (single sprite) — no round-robin variants, in contrast with the existing `Speeder1/2/3` set.
- New persisted setting `Settings.heroSkin: 'space-robot' | 'og-yellow'` (default `'space-robot'`). Mirrors the audience / audio-volume pattern: localStorage-backed observable, mutated via `Settings.setHeroSkin(...)`.
- The hero-picker call site (likely `pickRandomHeroSpriteKey()` in `spriteKeys.ts`, or its caller in `Hero.ts` / GameScene) consults `Settings.heroSkin`:
  - `'space-robot'` → always return `'space-robot'`.
  - `'og-yellow'` → existing random pick from `Speeder1` / `Speeder2` / `Speeder3` (current behavior preserved).
- `SettingsScene` → Game tab: new "Hero" row with a 2-option selector. Labels: "Space Robot" (with "default" hint) and "OG Yellow" (with "original" hint). Optional polish: thumbnail preview of each on the option button.
- `public/assets/CREDITS.md`: new entry for the Space Robot art (Midjourney-generated, project-owner prompted, per the existing CREDITS format).
- Sprite-asset loading: add the new key to `SPRITE_MANIFEST` so BootScene preloads it. Scope: `'always'` (it's the default; every session needs it on boot) — confirm at implementation; could move to `'game:alien-shoot'` if eager-boot transfer size matters.

**Open questions to settle at sprint-start:**

- **Scope across games:** does the skin choice apply ONLY to Alien Shoot's hero, or also to Asteroid Field's `asteroid-hero-*` set? **Recommendation:** Alien Shoot only for this story. Asteroid Field has its own three-ship round-robin set; a separate skin selector for that mode is a future story if the owner wants it.
- **First-run default:** new players default to `'space-robot'`. Existing players whose localStorage has no `heroSkin` key fall through to the same default — they see Space Robot on next visit; can switch to "OG Yellow" if they prefer. Confirm this is the intended migration behavior.
- **Animation:** the source is a single static image. Confirm no walking/running spritesheet is intended; if multi-frame is wanted later, that's a follow-up.
- **Settings tab placement:** the Game tab currently has the Asteroid Images toggle + audience controls. The Hero row fits there naturally; settle the row order.

**Acceptance:**

- New Space Robot sprite ships at `public/assets/sprites/hero/space-robot.webp`.
- Default Alien Shoot hero is Space Robot for new players + existing players with no `heroSkin` set.
- Settings → Game → Hero offers both options; the choice persists across page reloads.
- "OG Yellow" preserves the current 3-speeder random-per-round behavior unchanged.
- CREDITS.md updated.
- Typecheck clean; existing tests stay green.
