## Summary

Sprint 2.1 shipped two playable game modes but they shared the same backdrop AND the same music loop, so they felt visually + sonically interchangeable. This sprint gives each game mode its own audio-visual identity: a distinct background image and a distinct background music loop.

Story 1 was shipped retroactively in PR #31 (commit `b80e548`) before this sprint file existed — the per-game **background image** architecture (`GAME_BG_MAP` + `Settings.onGameIdChange` observer + `BackgroundScene` texture-swap). Documented here so the work is properly tracked in the sprint catalog rather than floating between sprints. Story 2 (per-game **music**) is the new work this sprint adds.

## Stories

### Story 1: Per-game-mode background images (RETROACTIVELY DOCUMENTED — shipped in PR #31)

**Type:** Code + asset

**Status:** Delivered 2026-05-17, merged to main as `b80e548`.

**Output (already shipped):**
- New asset: `public/assets/sprites/bg/asteroid-belt.png` (Midjourney-generated, 1280×717 RGB, brightness 0.6 matching the nebula recipe)
- `BgSpriteKeys.AsteroidBelt: 'asteroid-belt'` added
- `GAME_BG_MAP: Record<GameId, BgSpriteKey>` in `src/core/spriteKeys.ts` — central per-game-mode mapping; TypeScript exhaustiveness gives a compile error if a new GameId forgets to map a bg
- `Settings.onGameIdChange(listener) => unsubscribe` observer (mirrors the existing `onImageAsteroidsChange` pattern)
- `BackgroundScene` holds the backdrop image as a field, picks initial texture from `GAME_BG_MAP[Settings.round.gameId]`, subscribes to `gameId` changes to swap texture live
- CREDITS.md entry for `asteroid-belt.png`

**Flow:** `GameSelectScene` tile click → `Settings.setGameId(...)` → listener fires synchronously → `BackgroundScene` swaps backdrop → `DifficultyScene` renders over the new bg → game scene mounts over the already-correct bg. No flash, no incorrect-bg frame.

**Why this story is in 2.1.5 not 2.1.1:** I labeled the commit "Sprint 2.1.1" before the user established the formal sprint number. Retroactive cleanup: roll the work into 2.1.5 alongside the music story so both audio-visual-identity changes live in one tracked sprint.

### Story 2: Per-game-mode background music

**Type:** Code + asset (the bulk of this sprint)

**Output:**
- New asset: `public/assets/audio/music/loop-3.mp3` (30-second loop, encoded through `pnpm audio:encode` at music profile with `--no-trim` to preserve clean loop boundaries)
- `MusicKeys.Loop3: 'loop-3'` added to `src/core/audioKeys.ts`
- `GAME_MUSIC_MAP: Record<GameId, MusicKey>` in `src/core/audioKeys.ts` — parallel to `GAME_BG_MAP` (TypeScript exhaustiveness over GameId)
- Each game scene reads its music key from the map at scene mount instead of hardcoding `MusicKeys.Loop1`
- CREDITS.md entry for `loop-3.mp3`

**Mapping:**
- `alien-shoot` → `Loop1` (the existing menu/gameplay loop the user is used to)
- `asteroid-field` → `Loop3` (the new loop generated for this sprint)
- `loop-2.mp3` already exists on disk (orphaned from earlier processing) — left in place; not wired today but available as a future option

**Why a static map vs an `onGameIdChange` listener like the bg has:** music loops aren't started by the persistent `BackgroundScene` — they're started by individual game scenes via `getAudioManager().playLoop(...)` at `create` and stopped at `cleanup`. Each scene already knows its own gameId at create time, so it can just read `GAME_MUSIC_MAP[this.gameId]` directly. Adding a Settings listener here would be over-engineering vs the bg case (where the persistent `BackgroundScene` doesn't know when game scenes mount).

### Story 3: Session total score in HUD

**Type:** Code

**Output:**
- New module `src/services/SessionTotalScore.ts` — in-memory accumulator with `get()` + `add(delta)` + `reset()`. Page reload resets the total (same lifecycle as the existing `Settings._imageAsteroidsEnabled` module-scope flag). Unit-tested.
- HUD's top-left score label now shows TWO values:
  - `Round: N` — the current round's running score (was `Score: N` pre-sprint)
  - `Total: M` — accumulated session score across all rounds played since page load
- Each game scene's `endRound()` calls `SessionTotalScore.add(roundController.score)` BEFORE transitioning to GameOver — so a kid who plays 5 rounds in a sitting sees their cumulative score grow across sessions.
- HUD reads the session total on every `questionEnded` event + on scene mount (cheap; session total only mutates between rounds anyway).

**What does NOT change (per user direction):**
- High-score storage stays based on SINGLE-ROUND score (`SessionScoreStore` entries unchanged). The session total is a player-facing UX number, not a leaderboard concept.
- GameOver screen unchanged today (could add a "session total" callout in a follow-up sprint if playtest shows kids want it there too).
- Menu scenes unchanged.
