### Story 1: Mulligan UX hint — "One more try!" + −3s timer popup

**Type:** Code + polish (Support review must-fix #1)

**Status:** ✅ Shipped. NumberClimbScene's `handleWrongMulligan` now emits a `timePenalty` event + shows a session-once "One more try!" banner above the hero. HudScene listens for `timePenalty` and floats a red "−3s" popup at the countdown timer (new `penaltyPopup` TextKind + `TEXT_RED`, mirrors the `correctHit` → `popupScoreDelta` pattern). **Context:** Sprint 2.2 audit finding — when a kid picks a wrong rung in Number Climb, the rung dims and the hero falls back, but they get NO visual cue that they have only ONE retry. A first-time player can think the wrong rung is just disabled and freely guess again, then be surprised when the second wrong ends the round.

**Output:**
- On the first mulligan of a kid's first session (sessionStorage flag), show a brief "One more try!" banner above the hero for ~1.5 s.
- On every mulligan, render a floating "−3s" popup at the timer (mirror the existing `correctHit` score-popup pattern from Alien Shoot) so the kid registers that time was the cost.

**Acceptance:**
- First mulligan ever in a session: "One more try!" banner appears, fades after 1.5 s.
- Every mulligan: "−3s" red text floats up from the timer for ~800 ms.

### Story 6: WebP migration for backgrounds + sprite art

**Type:** Code + assets (DevOps review nice-to-have #2)

**Status:** ✅ Shipped. `scripts/sprites/process.mjs` gained a `--format <png|webp|webp-lossless>` flag (sharp's WebP encoder; lossy q85 / lossless, effort 6). Migrated 36 assets: 21 `bg` images (19 climb floors + nebula + asteroid-belt) → lossy q85, 7 `hero` sprites + 8 Asteroid Field rocks → lossless. Old PNGs deleted. `spritePath()` now resolves `.webp` for the `alien`/`bg`/`hero` kinds (new `WEBP_KINDS` set), `.png` for `ui`/`particle`/`projectile`; the asteroid manifest entry's hardcoded URL flipped to `.webp`. Result: bg payload **~9.5 MB → ~1.0 MB** (≈90 % smaller); heroes ~12 % smaller. Title splash deferred to sprint 2.5 (it reworks that art anyway). Typecheck + build + 348 tests green. Visual QA done — the lossy-q85 floor backgrounds were eyeballed in the Story 12 playtest pass, no artifacts.

**Context:** Number Climb's 19 floor PNGs total ~5.5 MB. Sprite pipeline currently outputs PNG only. WebP is universally browser-supported (Safari since 14, Phaser handles it natively — alien spritesheets are already WebP). Migration saves ~4 MB on the Climb game-bundle download + ~1 MB on boot for backdrops.

**Scope (decided during sprint planning):**

| Asset family | Files | Mode | Expected savings |
|---|---|---|---|
| Floor backgrounds | 19 (climb-floor-fire, escape, room-1..16) | **lossy q85** | ~60 % → ~3.3 MB |
| Game backdrops | 2 (nebula, asteroid-belt) | **lossy q85** | ~60 % → ~850 KB |
| Title splash | 2 (Title-Splash-1, -2) | **lossy q85** | ~60 % → similar |
| Hero ships | 7 (speeders + asteroid-heroes + escape-ship) | **lossless** | ~25 % → ~30 KB |
| Asteroids | 8 (asteroid-1..8) | **lossless** | ~25 % → ~30 KB |
| UI sprites | n/a | skipped | already tiny |
| Particle sprites | n/a | skipped | already tiny |

Lossy q85 for no-alpha backgrounds (no edge-halo concern, 60% savings). Lossless for alpha sprites (clean transparent edges, smaller absolute savings but consistent quality).

**Output:**
- Extend `scripts/sprites/process.mjs` to support `--format webp` (lossy q85) and `--format webp-lossless` flags. Sharp already supports WebP output natively (`sharp(...).webp({ quality: 85 })` or `.webp({ lossless: true })`); the change is parsing the new flag + dispatching the encoder.
- Re-process all 36 in-scope assets through the new pipeline. Move existing `.png` files to `.sprite-source/raw/processed/` or delete (per audio-pipeline convention).
- Update `spritePath()` / `SPRITE_MANIFEST` to use `.webp` extensions for the migrated assets. Two paths to consider:
  - **Option A**: change `spritePath` to return `.webp` for the migrated kinds; force-route in one place.
  - **Option B**: per-entry `extension` field on SpriteManifestEntry. More flexible, more LOC.
- Verify Phaser loader handles `.webp` for non-spritesheet single images (it does — used by alien spritesheets — but a manual smoke-test confirms).
- Manual playtest all three game modes to confirm visual quality (especially the floor backgrounds at lossy q85).

**Acceptance:**
- Number Climb game-bundle download drops by ~3 MB.
- Boot bundle drops by ~1 MB (nebula + asteroid-belt).
- Hero + asteroid sprites visually identical (lossless), backgrounds visually indistinguishable from PNG at normal viewing (lossy q85).
- All 337 tests still pass.
- `pnpm build` succeeds; build output reflects the smaller asset payload.

### Story 11: Cross-game max-score calibration (Easy / Medium / Hard)

**Type:** Code (audit + adjust scoring multipliers)

**Folded in from the former sprint 2.3.**

**Status:** ✅ Shipped as a **verification** — no calibration needed. Analysis: `ScoreCalculator`'s constructor is `(mathId, speed)` with NO game-mode axis; score per correct = `basePerCorrect × mathMultiplier × speedMultiplier`, all three terms game-agnostic. After Story 10 all three games run 12-question rounds. So a perfect round already produces an IDENTICAL max score across Alien Shoot / Asteroid Field / Number Climb for the same (mathId, speed) — `12 × 100 × mathMult × speedMult` (Easy add-to-10 = 1200, Medium = 1500, Hard = 1800). The per-game mechanics (wrong-shot penalty / timeout / mulligan) only reduce a round BELOW max, never change the max — so no per-game adjustment multiplier was added (one would have *broken* the equal-max goal). 4 new parity tests in `ScoreCalculator.test.ts` lock the invariant. 344 → 348 tests.

**Context:** With Story 10 normalizing all three games to 12 questions, the theoretical max score per game at each difficulty SHOULD be identical — but only if the scoring formula's inputs match across modes. `ScoreCalculator.recordOutcome` computes `basePerCorrect × mathDifficulty × speedMultiplier × wrongShotMultiplier` globally — same formula for all three games. But mode-specific scoring nuances may drift the max:
- **Alien Shoot:** descending-alien wrong-shot penalty reduces score over the round.
- **Asteroid Field:** per-question countdown — running out of time scores 0 for that question.
- **Number Climb:** one mulligan per floor — first wrong rung halves that floor's points; cumulative timer-out ends the round early.

A kid playing perfectly on Easy should walk away with the same max score regardless of game. If not, the Phase 3 cross-game leaderboard becomes "which game is most generous" rather than "who's best at math."

**Output:**
- Compute the THEORETICAL MAX score for each (game × difficulty) combo assuming a perfect round: `12 correct × basePerCorrect × mathMultiplier × speedMultiplier`, with `mathMultiplier` fixed to a reference (e.g. `add-to-10` = 1.0) since math choice is orthogonal to game choice.
- Document the 3×3 max-score grid in a table.
- If any cell differs from another at the same difficulty: identify the diverging game-specific multiplier; converge it (preferred) or document the intentional divergence.
- Likely fix: a small per-game difficulty-adjustment multiplier (`Record<GameId, number>` for ADR-0011 exhaustiveness) so a perfect Climb-Hard round and a perfect AsteroidField-Hard round produce the same max.
- Add `ScoreCalculator.test.ts` assertions locking cross-game parity at each difficulty.

**Acceptance:**
- A perfect Easy round of any of the three games produces the same final score. Same for Medium, Hard.
- Math-difficulty multiplier still varies (add-to-10 vs div-to-144); only the game-mode axis is normalized.
- New parity tests guard against future desync.
