# Sprint 2.9: Subjects foundation — topic-first flow

**Phase:** 2
**Status:** Planned — awaiting the design review (Story 1)
**Closed:** —
**Released:** —
**Blocks:** The next game modes (Pair Pals, Number Line Hop, …) and any non-math subject.
**Depends on:** 2.8 (Released).
**Estimated effort:** 3–4 days across three releasable steps, plus the owner's naming decision.

## Summary

An architecture sprint: no new games. It gets the app ready to grow beyond math as **one umbrella app** (the owner's direction, 2026-10-19), which is also what a future Android / iOS wrap would need.

It ships in three steps, each releasable on its own:

1. **Topic-first flow (2.9.0).** What you practise ("Add to 10", now the *topic*) is chosen on Game Select and stays put while you hop between games. Difficulty is still chosen per game, so each game keeps its own labels ("3 holes · 25s"). Players see the change.
2. **Subject → topic model (2.9.1).** "Math type" becomes a topic inside a subject (Math). There's still only one subject, so players see no change; the code is ready for a second.
3. **Name and store-app assessment (decisions, no code).** The umbrella name (the owner's call) and a written assessment of wrapping the app for the app stores.

## Decisions (owner, 2026-10-19)

- **One umbrella app**, subject → topic. No cloned repos and no family of sites.
- **The topic is chosen on Game Select**, and it must be easy to swap there.
- **Difficulty stays per game**, chosen after the game, so it keeps the per-game labels.
- **A new umbrella name** is needed before a second subject ships: "mathBasher" won't fit words.
- The next-game ideas (Pair Pals, Number Line Hop, Balance Scale, Kitty Café, Pattern Train, two-player duel) are parked until this sprint lands.

## Design (draft, for the review)

### D1. The new screen flow (step 1)

| | Today | After |
| --- | --- | --- |
| Menu → | Game Select | Game Select, with a **topic chip** at the top: "Practising: Add to 10 ✎" |
| Game Select → | Difficulty (math type + difficulty) | Difficulty (**difficulty only**, the same per-game labels), with the topic shown as a chip |
| Difficulty → | Loading → game | unchanged |
| Pause / Game Over → Change Game | Game Select (math type and difficulty kept) | unchanged |
| Game Over → Change Difficulty | Difficulty | Difficulty (difficulty only) |

- **Topic chip:** a big, obvious pill at the top of Game Select ("Practising: Add to 10 ✎"). Tapping it opens the **topic picker**: the math types as today (whole numbers, then fractions), the current one highlighted. Pick one and you're back on Game Select. The chip is also on the Difficulty screen, so the topic can be changed there without going back.
- **First visit:** no topic yet → the picker opens by itself the first time Start is pressed, or a default (Add to 10) is preselected. The review picks one.
- **Remembered:** the topic and each game's last difficulty are kept for the visit (today they're in memory only). Whether they survive a reload (localStorage, like the hero choice) is a review question.
- **Keyboard:** the chip is the first stop on Game Select and on Difficulty; Esc in the picker closes it.
- **Difficulty screen:** loses the Math Type section, so the difficulty buttons and Start get more room and bigger targets on a phone.
- **Telemetry:** `TopicChanged` (with `mathId`), and the screen events follow the new order.

### D2. Subject → topic model (step 2)

- **Names:** `SubjectId` (today only `'math'`), `TopicId` (today the existing `MathId` values). A small registry maps subject → topics → question generator and display metadata (label, section, "coming soon").
- **Question layer:** the `Question` shape (prompt, choices, right answer, displays) already fits other subjects. The generator registry moves from math-only to subject-aware; the math generators don't change.
- **Game support:** each game lists the answer kinds it can show (whole numbers, fractions, later words). Game Select greys out a game that can't play the current topic (none today).
- **Answer labels:** `MathText` keeps the mixed-number rule; a word answer needs its own fit-and-shrink check in every game's carrier (alien, rock, rung, bubble, pad, ship, fish, carrot sign). This sprint adds the check, not the words.
- **Kept stable:** the `mathId` telemetry property (cross-version queries), the `round.mathTimeScale` and scoring tables (keyed by topic), and the persisted settings keys.
- **One subject:** with only Math, the picker shows no subject step, so nothing changes for players.

### D3. Name and store-app assessment (step 3, decisions only)

- **Name:** where "mathBasher" appears today (title, splash, page title, footer, web manifest, README, repo, domains), what changes for a rename and in what order (the app first; the repo and domains can follow). The owner picks the name.
- **Store app:** wrapping options (for example Capacitor), offline assets, the kids-store rules (Google Families, Apple Kids Category) and COPPA. What that pulls forward from Phase 4 (privacy policy, analytics review, a parent gate in front of links and settings). Recorded as an ADR, so it can be scheduled later.

## Stories

### Story 1: Design review
Architecture, senior dev, kid UX / support and legal review the draft against the code. Open questions for the review: first-visit behaviour (picker or default), whether the topic and difficulty survive a reload, the chip's size and wording for young readers, and the module boundaries for subjects.
**Output:** this file, updated with the findings.

### Story 2: Topic-first flow (ships as 2.9.0)
**Output:** Game Select topic chip + topic picker; Difficulty without the Math Type section (with the chip); Settings (topic and per-game difficulty remembered); keyboard and Esc; telemetry; tests; a browser playtest of every path (first visit, chip swap, Change Game, Change Difficulty, Play Again, pause → Change Game) on a phone-sized screen.

### Story 3: Subject → topic model (ships as 2.9.1)
**Output:** `SubjectId` / `TopicId` and the subject registry; the question layer made subject-aware; per-game answer-kind support; the word-label fit check; ADR-0014 (subjects and the topic-first flow); ADR-0011's checklist updated; no visible change (tests prove the same questions come out).

### Story 4: Name and store-app assessment
**Output:** a name inventory and rename plan (the owner picks the name); ADR-0015 (store-app options and what they require). No code.

### Story 5: Docs + review + close
**Output:** `VERSIONS.md`, `package.json`, `src/game/PLAYTEST.md`, `DeveloperGuide.md`, `.sprints/SPRINT-PLAN.md`; the sprint review for each release.

## Definition of done
- **Checks:** format check, lint, typecheck, tests and build pass.
- **Playtest:** every path in Story 2 on a phone-sized screen and on desktop; the owner's phone check on dev.
- **No regressions:** all eight games play every math type exactly as before.
- **Release:** each step only after the owner's go.
