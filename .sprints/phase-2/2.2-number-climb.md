## Summary

Third game mode for mathBasher: a vertical climbing platformer where the kid hops between rungs at each floor, picking the rung that carries the correct answer to a math prompt. The hero climbs 10 floors total — fully achievable max score if you make it to the top.

Key gameplay differences from existing modes:
- **Vertical motion** (vs. Alien Shoot's lane-drop, Asteroid Field's static rotate-aim).
- **Difficulty controls choice count** (2/3/4 rungs per floor for Easy/Medium/Hard) — orthogonal to Speed.
- **Speed controls cumulative timer** (250s/180s/120s budget for the whole climb at Slow/Medium/Fast).
- **One mulligan per floor.** First wrong rung on a floor: −3s time penalty + `hit-wrong-3.mp3` SFX + hero falls back to that floor's base + half points on the eventual correct answer. Second wrong on the same floor: round ends.
- **Timer-to-zero also ends the round.**
- **Stars by height reached** (not correct-count): 1 star = floor 4+, 2 = 7+, 3 = top (floor 10).
- **Round size: 10 floors** (vs. 20 questions in other modes — shorter rounds soften the one-strike-on-second-wrong harshness + give Climb its own pacing).

## Open-question answers (decided 2026-05-18 / 2026-05-19)

1. **Climbing model** — 4-rungs-above-hero (with difficulty-based rung count) ✓
2. **Round size** — 10 floors (not 20) ✓
3. **Wrong-rung policy** — 1 mulligan per floor; second wrong on same floor ends round ✓
4. **Timer** — cumulative across whole climb; wrong rung subtracts 3s ✓
5. **Speed setting** — controls cumulative timer length ✓
6. **Stars** — height-based (4/7/10) ✓
7. **"Pass"** — reached the top (floor 10) ✓
8. **SFX for wrong rung** — `hit-wrong-3.mp3` (existing asset) ✓
9. **Input model** — tap-commit (click/tap a rung directly; no positioning). Keyboard: number keys 1-N pick rungs left-to-right with visible "N." prefix on each rung. Same single-action model as Alien Shoot + Asteroid Field. Will pivot to drag/positioning if playtest shows a real need. ✓

## Placeholder-asset strategy during dev

The implementation order is: stories 2-12 (gameplay + wiring) first; story 1 (real art delivery) at the end. To let the gameplay land WITHOUT broken asset references in the meantime:

- **`GAME_BG_MAP['number-climb']` points temporarily at `BgSpriteKeys.Nebula`** until story 1's real climb-tower bg arrives.
- **`GAME_MUSIC_MAP['number-climb']` points temporarily at `MusicKeys.Loop1`** until story 1's climb music arrives.
- **`GAME_MIDGROUND_MAP['number-climb']` points temporarily at `MidgroundKeys.Skittering1`** until story 1's climb-ambient arrives.
- **NumberClimbHero** uses procedural rectangle/colored-circle rendering during dev. Real hero sprite swaps in via the `pickRandom...` pattern (sprint 2.1 precedent) when art arrives.
- **Rungs** use procedural Graphics rectangles with text overlays during dev. Real rung sprite swaps in later.

Story 1's wrap-up swaps the placeholder mappings to the real keys + adds the manifest entries with `scope: 'game:number-climb'` so the assets lazy-load via the existing `loadGameBundle` infrastructure.

Validation gate: the sprint does NOT merge until real art has landed (so the public release has the final visuals).

### Story 7: NumberClimbFloorSystem (the "wave system" equivalent)

**Type:** Code (the core gameplay primitive)

**Output:**
- `src/game/systems/NumberClimbFloorSystem.ts` — owns the floor + rung lifecycle.
- `spawnFloor(question: Question, floorIndex: number)`: creates the N rungs above the hero (N from difficulty: 2/3/4), each rendered with one of `question.choices` as the visible answer. Distributes rungs horizontally across the playfield with sensible spacing.

- Tracks `wrongsThisFloor` (0 or 1 after first mulligan, 2 ends the round).
- `clearFloor(instant)`: tears down current floor's GameObjects.
- Subsystem `pause()` / `resume()` hooks for the lifecycle.
- Unit-testable: hit-detection math is pure; scene/Phaser dependencies passed via constructor.

**Acceptance:** Spawning a floor produces N rungs with answers; picking a rung correctly advances the floor; picking wrong once shows the mulligan; picking wrong twice ends the round.

### Story 13a: Per-floor background image + framed-floor visual treatment

**Type:** Code + assets

**Context:** Right now Number Climb inherits the global `BackgroundScene` (nebula + 3 layers of parallax stars). The falling stars assume an arcade vertical-shooter pass-through (Alien Shoot, Asteroid Field) where the player sees the sky overhead. In Climb the player is INSIDE a tower — there is no overhead view of stars to scroll past. The stars are wasted overhead.

The Climb visual wants to look like the kid is climbing through framed "rooms" stacked vertically. Each floor is a discrete scene framed by:
- **Vertical black bars** down the left + right edges (let the nebula show through on the sides — confirms the climb is happening inside an environment, not a void).
- **Horizontal thick black bar** between floors — the floor separator (acts as the "ceiling of floor N" / "floor of floor N+1").
- **A single per-floor background image** filling the framed area (the "room" of that floor).

Per-floor image proportions: `--ar 8:1` (1920×240 source) — matches the floor's natural aspect (`FLOOR_SPACING_PX = 110` × ~`1264` playfield-wide). The 8:1 aspect gives MJ enough vertical room to compose without smearing while still cropping/scaling cleanly to the 110px floor band.

**Output:**
- `BackgroundScene` learns to suppress its falling-star layers when `Settings.round.gameId === 'number-climb'` (the nebula stays for the side-frame bleed). The `onGameIdChange` subscription already in `BackgroundScene` is the right hook — add a star-visibility toggle alongside the existing backdrop swap.
- New asset entry: ONE Midjourney `--ar 8:1` floor image (kebab-case name like `number-climb/floor-room-1`). Run through `scripts/sprites/process.mjs` (existing sprite pipeline) → outputs the WebP variants. Manifest entry with `scope: 'game:number-climb'`.
- New `spriteKeys.ts` entry: `ClimbFloorBgKeys.Room1` (extensible enum so story 13b can add Room2..N).
- New file `src/game/entities/NumberClimbFloorFrame.ts` (or a helper inside `NumberClimbFloorSystem`) that, for each spawned floor:
  - Renders the per-floor bg image scaled to fit the 110px floor band (full playfield width minus the side-frame inset).
  - Renders the left + right vertical black bars (recommend 16–24px wide, color `0x000000`, full floor height).
  - Renders a thick horizontal black bar at the TOP of the floor (recommend 4–6px, color `0x000000`, full playfield width) — this doubles as the visual ceiling of the previous floor.
- Order in the scene's display list: framed bg sits BELOW the rungs + hero. Rungs and hero must remain pinned to the top of the floor (no overlap with the side-frame bars; the playfield distribution math may need a small inset adjustment so rungs don't kiss the frame).
- Bottom of the bottom-most floor renders an additional horizontal bar (the "ground"), so floor 1 looks closed off.

**Acceptance:**
- Loading Climb shows the nebula on the left + right margins (outside the frame) and the floor-bg image inside.
- No falling stars visible during Climb.
- Other modes (Alien Shoot, Asteroid Field) are UNAFFECTED — they still see stars + nebula as today.
- Floor separators are crisp + readable; the kid can visually count the floors as they climb.
- Hero + rungs render above the frame; no z-order glitches.

### Story 13b: Preview the next floor at reduced opacity

**Type:** Code + polish

**Context:** With Story 13a in place, the kid climbs through framed floor "rooms" and sees the stack of completed floors below them. But they have NO visual hint about what's coming next — the climb feels reactive ("solve this floor, then the next one appears") rather than anticipatory ("I can see I'm climbing TOWARD a goal up there"). Surfacing the next floor's bg image as a faint preview above the current floor turns the climb from "blind sequence" into "visible path upward." Targets the kid playtesting feedback dynamic where seeing the destination is more motivating than not.

**Output:**
- New `nextFloorPreview: NumberClimbFloorFrame | null` field on `NumberClimbFloorSystem`. Holds the pre-spawned reduced-alpha frame for the floor ABOVE the current one.
- `spawnFloor` does TWO frame-spawns per call:
  1. If `nextFloorPreview` exists, **promote it** — tween its alpha from 0.25 → 1.0 over ~300ms, push it onto the `frames` array. Don't create a new frame for the current floor (the previously-spawned preview becomes the current floor).
  2. If we're not at the last floor, **spawn a fresh preview** for floor N+1: a new frame at the next floor's y position, picked bg key, alpha 0.25. Stored in `nextFloorPreview`.
- Edge case: on the very FIRST `spawnFloor` call (no preview exists), spawn the current floor frame normally (at full alpha) PLUS a preview for the floor above.
- Edge case: on the last floor (`floorReached + 1 === totalFloors`), promote the preview but DON'T spawn a new one beyond it. (Optional: replace with a small "TOP" capstone visual — out of scope unless cheap.)
- `pickRandomClimbFloorBgKey` is called at PREVIEW spawn time, not at promote time, so the bg key the kid sees in the preview is the same one they get when they actually arrive at that floor.
- `clearAllFrames()` (scene shutdown) now also destroys `nextFloorPreview` if present.

**Trade-off worth noting in the implementation comment:**
- The kid sees the floor's bg BEFORE arriving — replaces "surprise" with "anticipation." The design call (sprint 2.2 conversation) is that anticipation is better for the target age group than surprise.
- Slight visual noise increase (two floor images on screen instead of one) — Story 13a's black side-bars + horizontal separators are what keep this readable; the preview's reduced alpha makes the current floor still dominant visually.

**Acceptance:**
- Playing Climb, the kid can see a faint "next floor" hint above the current one from the start of every floor.
- The preview alpha tweens up smoothly when the kid climbs onto it — no pop, no flicker.
- The bg image visible in the preview matches the bg image shown when the kid arrives at that floor (i.e., the bg key is stable across the promote).
- Top floor doesn't render a "next" preview beyond itself.
- No new test failures; existing 337 tests stay green.
