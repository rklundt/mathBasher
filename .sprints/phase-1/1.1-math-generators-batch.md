# Sprint 1.1: Phase 1 math generators batch (1.1 + 1.2 + 1.3 + 1.4 bundled)

**Phase:** 1
**Status:** Closed (2026-05-16)
**Released:** v1.1
**Blocks:** 1.5 Division (depends on multiplication landing first), 1.6 Mixed
**Depends on:** 0.7.5 Mobile + speed tuning (closed 2026-05-15) — establishes typography + telemetry baseline that new generators inherit transparently.
**Estimated effort:** 0.5–1 day planned; actual ~1 day across 9 commits (8 substantive + 1 wrap-up polish). Story list grew from the original 8 to 16 effective changes as playtest surfaced fixes (HudScene dot regression, speeder facing direction, chassis widening for aim, anti-repeat sliding window for prompt repetition).

## Summary

Implement the Phase 1 math generators as a single sprint increment per user direction ("start-sprint 1.1 through 1.4 as one sprint increment"). User additionally split row 1.4 into two tiles: "multiply 10×10 and a separate tile for 12×12." Five new generators total. Each is a near-identical pattern lift from `addTo10.ts`:

1. Write the generator file under `src/math/generators/`
2. Replace the registry stub (or add new entry for the multiplication tiers) in `src/math/registry.ts`
3. Add a test file modeled on `addTo10.test.ts`

For multiplication ONLY, also add new keys to `config.scoring.mathDifficulty` (the additive ones — `add-to-20`, `sub-to-10`, `sub-to-20` — are already pre-registered as stubs from sprint 0.2). After this sprint closes, the DifficultyScene tile grid auto-enables all 6 tiles (no scene code changes needed — DifficultyScene reads `getImplementedIds()` and the `gen.label` / `gen.description` per tile).

**Why bundled rather than 5 separate sprints:** each individual sprint would be ~30 minutes of work plus the overhead of branch + PR + wrap-sprint + close-sprint × 5. The variance between the five generators is small (range bounds, operator symbol) and they share the same test scaffolding. One PR, one six-reviewer audit, one tag.

**DifficultyScene capacity check:** with 6 enabled tiles at 220px wide + 20px gaps, the row totals 6 × 220 + 5 × 20 = 1420px — overflows the 1280px design canvas by 140px. Sprint 0.7.5 Story 5 sized tiles for 4 across; 6 across needs a layout decision. Likely solutions: (a) shrink tiles to 200px (6 × 200 + 5 × 20 = 1300, still overflows by 20), (b) use 180px tiles (6 × 180 + 5 × 20 = 1180 — fits), or (c) re-flow into two rows of 3. Story 8 below addresses this.

## Stories

### Story 1: `add-to-20` generator

**Type:** Code

**Output:**
- `src/math/generators/addTo20.ts` mirroring the structure of `addTo10.ts`
- `src/math/generators/addTo20.test.ts` mirroring `addTo10.test.ts`
- Registry stub for `add-to-20` in `src/math/registry.ts` replaced with the real import

**Math spec** (per SPRINT-PLAN row 1.1: "sums where each addend is 1-10, total up to 20"):
- Two addends `a, b ∈ [1, 10]`
- Sum `a + b ∈ [2, 20]`
- Sum drawn first uniformly from `[2, 20]`, then `a` drawn uniformly from the valid range that allows `b ∈ [1, 10]` (i.e. `a ∈ [max(1, sum-10), min(10, sum-1)]`), `b = sum - a`
- This preserves the answer-uniformity property addTo10 established (every answer value gets equal exposure)
- Distractors: 3 distinct integers from `[2, 20]` not equal to the correct sum

**Acceptance:**
- 1000 seeded samples: every prompt parses to two integers, both in `[1, 10]`, summing to a value in `[2, 20]`, matching `correctAnswer`
- Choices always length 4, always include the correct answer, no duplicates
- `getImplementedIds()` includes `'add-to-20'`
- `pnpm typecheck` / `pnpm test` green

### Story 2: `sub-to-10` generator (Subtract within 10)

**Type:** Code

**Output:**
- `src/math/generators/subTo10.ts`
- `src/math/generators/subTo10.test.ts`
- Registry stub for `sub-to-10` replaced

**Math spec** (per SPRINT-PLAN row 1.2):
- Minuend `a ∈ [0, 10]`, subtrahend `b ∈ [0, a]` (no negative results — kid-friendly)
- Result = `a - b ∈ [0, 10]`
- Result (= correctAnswer) drawn uniformly from `[0, 10]`, then `a` drawn uniformly from `[result, 10]`, `b = a - result`. Same answer-uniformity reasoning.
- Distractors: 3 distinct integers from `[0, 10]` not equal to the result

**Acceptance:**
- 1000 seeded samples: prompt parses to `a - b = ?` form, `a ∈ [0, 10]`, `b ∈ [0, a]`, `a - b ∈ [0, 10]`, matches `correctAnswer`
- Choices always length 4, always include correct answer, no duplicates
- `getImplementedIds()` includes `'sub-to-10'`

### Story 4: `mult-to-100` generator (Multiply 10×10) + new config key

**Type:** Code (slightly larger than 1-3 because of the new config key)

**Output:**
- `src/math/generators/multTo100.ts`
- `src/math/generators/multTo100.test.ts`
- New entry in `config.scoring.mathDifficulty`: `'mult-to-100': 2.5` (multiplier higher than `sub-to-20`'s 2.0 because mult tables are harder than subtraction within 20). Comment in config.ts explains: per the existing pattern, addition base = 1.0, subtraction = +0.5 over add at same range, "to 20" version = +0.5 over "to 10" version.
- Registry entry for `mult-to-100` (no stub to replace — brand-new key)

**Math spec** (covers SPRINT-PLAN row 1.4 part 1 — standard elementary curriculum, factors 2-10):
- Factors `a, b ∈ [2, 10]`
- Product = `a × b ∈ [4, 100]`
- Both factors drawn uniformly from `[2, 10]` (NOT product-uniform — many products have only one factor pair, e.g. 4 = 2×2 only, vs. 12 = 2×6 = 3×4 = 4×3 = 6×2). Factor-uniform is the right pedagogical choice ("see every multiplication fact equally often").
- Operator rendered as `×` (Unicode U+00D7), NOT ASCII `x` — `x` reads as a variable
- Distractors: 3 distinct integers from `[4, 100]` not equal to the product
  - Note: distractor pool is large (96 candidates after excluding correct), so `pickDistractors` works fine
  - Future improvement out of scope: bias distractors toward "near-miss" products (e.g. 7×8=56 → distractors `48, 54, 63` instead of random ints) — that's its own sprint

**Acceptance:**
- 1000 seeded samples: prompt parses `(\d+) × (\d+) = \?`, both factors in `[2, 10]`, product matches
- Choices always length 4, always include correct answer, no duplicates
- New `mult-to-100` key visible in `Object.keys(config.scoring.mathDifficulty)`
- `getImplementedIds()` includes `'mult-to-100'`
- DifficultyScene tile auto-renders with `gen.label = "Multiply 10×10"` and `gen.description = "Tables up to 10×10."` (final copy TBD during implementation)

- Registry entry for `mult-to-144`

**Math spec** (covers SPRINT-PLAN row 1.4 part 2 — extended tables, factors 2-12):
- Factors `a, b ∈ [2, 12]`
- Product = `a × b ∈ [4, 144]`
- Same factor-uniform sampling and Unicode `×` operator as Story 4
- Distractors from `[4, 144]` (140 candidates after excluding correct — plenty)

**Acceptance:**
- 1000 seeded samples: factors in `[2, 12]`, product matches
- Choices always length 4, always include correct answer, no duplicates
- New `mult-to-144` key visible in config + registry
- `getImplementedIds()` includes `'mult-to-144'`
- DifficultyScene tile auto-renders with `gen.label = "Multiply 12×12"` and `gen.description = "Tables up to 12×12."`

**Why two separate tiles (not one bigger one):** per user direction ("multiply 10x10 and a separate tile for 12x12"). Pedagogically: 10×10 is the standard elementary curriculum endpoint; 12×12 (the traditional "times tables" range) is a clear next-step level for a kid who's mastered 10×10. Splitting them gives a kid an explicit "I conquered the 10s, now I'm ready for 12s" progression marker.

**Configurability follow-up:** SPRINT-PLAN row 1.4 originally mentioned "configurable subset" of mult tables — i.e. a future kid-facing setting "I only want 7×, 8×, 9× today." Out of scope for THIS sprint (no UI). Add a TODO comment in BOTH `multTo100.ts` and `multTo144.ts` so a future sprint knows where to plumb a `factorSubset?: number[]` option through.

### Story 6: Distractor-quality spot-check across all 6 implemented generators

**Type:** Test

**Output:**
- A new test file `src/math/distractor-quality.test.ts` (or extend existing `distractors.test.ts`) that runs 200 seeded samples per generator and asserts:
  - Distractors are always distinct from the correct answer
  - Distractors are always distinct from each other (no duplicate choices)
  - Distractors fall within the documented range for that generator

**Acceptance:**
- Test covers all 6 implemented generators (`add-to-10`, `add-to-20`, `sub-to-10`, `sub-to-20`, `mult-to-100`, `mult-to-144`) in one place
- Catches the class of bug where a future generator forgets to call `pickDistractors` correctly

**Why this exists:** the per-generator test files cover math correctness, but a cross-cutting "no generator silently emits a duplicate choice" rule is easier to enforce in one place. Cheap insurance.

### Story 8: DifficultyScene math-tile layout reflow (4-across → 4-across × 2 rows)

**Type:** UI tweak (no math-engine change; existing DifficultyScene re-tune)

**Origin:** with 6 enabled tiles after Stories 1-5, the current single-row 4-across layout (sized 220×100 in sprint 0.7.5) overflows: 6 × 220 + 5 × 20 = 1420px in a 1280px design canvas. Need to reflow.

**Output:**
- `DifficultyScene.renderMathTypes`: rewrite to lay out tiles in a 4-per-row grid wrapping to multiple rows. With 6 tiles → 1 full row (4 tiles) + 1 partial row (2 tiles, centered).
- Default to 4 per row so the layout matches the prior visual cadence (Phase 0.7.5 already sized tiles + spacing for 4-across); the second row is shorter when total isn't a multiple of 4.
- Speed row + Start/Back row Y positions may need to shift down to accommodate the second math row. Math row 1 stays at `height * 0.34`; math row 2 at `height * 0.34 + 100 + 16` (tile height + 16px row gap); Speed row goes from `0.66` → `0.78`; Start/Back from `0.85` → `0.92`. Tight against the footer — verify clearance.
- Alternative future scaling: when Phase 1.5 (division) + 1.6 (mixed) land, the grid becomes 8 tiles → 2 rows of 4 fits cleanly without another layout pass.

**Acceptance:**
- Manual: open DifficultyScene → 6 tiles render across 2 rows (4 in row 1, 2 centered in row 2)
- Manual: Speed row + Start/Back row remain visible and don't collide with the AGPL footer
- Manual: keyboard Tab order flows correctly through both math rows then Speed then Start then Back
- Section labels ("Math Type", "Speed") still clear the tile tops cleanly (the y-90 / y-75 offsets from sprint 0.7.5 Story 5 still apply, no change to those offsets needed)

**Why included in this sprint:** the layout overflow is caused BY this sprint's new tiles. Splitting Story 8 into a separate sprint would mean shipping a broken-layout intermediate state. Bundled here.

**Out of scope:** any visual polish (drop shadows, hover animations, etc.) — this is geometry only.
