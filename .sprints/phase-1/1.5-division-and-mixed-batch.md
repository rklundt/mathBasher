## Summary

Closes out Phase 1 by bundling rows 1.5 (Division) + 1.6 (Mixed) per user direction ("A: bundle 1.5+1.6"). Same shape as the 1.1 bundle — multiple small additive deliverables in one sprint, one PR, one tag.

**Three new generators total:**

1. **`div-to-100` "Divide 10×10"** — inverse of `mult-to-100`. Divisor + quotient both in [2, 10]; dividend in [4, 100]. Sampling guarantees integer result (sample factors first, then compute dividend = factor × quotient).
2. **`div-to-144` "Divide 12×12"** — inverse of `mult-to-144`. Divisor + quotient in [2, 12]; dividend in [4, 144]. Same sampling shape.
3. **`mixed` "Mixed"** — at draw time, picks one of the 8 implemented math types at random and returns ITS question. Reports `mathId: 'mixed'` to telemetry + ScoreCalculator (single multiplier representing the average difficulty).

**Why splitting division into two tiles** (mirroring multiplication): the SPRINT-PLAN row 1.5 was originally one row, but the 1.1 sprint set the pattern that the "10×10" / "12×12" split matches the curriculum's natural levels — 10×10 is standard elementary, 12×12 is the extended traditional tables range. Same logic applies to division. A kid who masters 10×10 multiplication will recognize the division-by-10×10 inverse and feel rewarded; same for 12×12.

**Why Mixed isn't multi-select for v1**: the SPRINT-PLAN description says "random pick from selected operations" — implying user picks WHICH operations to mix. For v1, "selected" = "all implemented" (the system selects them all). A future sprint can add a multi-select checklist UI in DifficultyScene. This sprint scope: one Mixed tile that randomly draws from all 8 other implemented math types.

After this sprint closes, DifficultyScene will show **9 enabled math tiles**: row 1 (4 tiles: add-to-10, add-to-20, sub-to-10, sub-to-20), row 2 (4 tiles: mult-to-100, mult-to-144, div-to-100, div-to-144), row 3 (1 tile: Mixed, centered). The grid-layout code from sprint 1.1 Story 8 already handles partial last rows (centers them automatically); only the Speed/Start/Back Y anchors need adjusting to accommodate the new third math row.

## Stories

### Story 1: `div-to-100` generator (Divide 10×10) + new config key

**Type:** Code

**Output:**
- `src/math/generators/divTo100.ts` mirroring the structure of `multTo100.ts`
- `src/math/generators/divTo100.test.ts` mirroring `multTo100.test.ts`
- New entry in `config.scoring.mathDifficulty`: `'div-to-100': 3.5` (per the multiplier ladder pattern — +0.5 over `mult-to-144` because inverse multiplication is a step harder than direct multiplication at the same factor range, even though the factors are smaller than the 12×12 step)
- Registry entry for `div-to-100`

**Math spec:**
- Divisor `d ∈ [2, 10]`, quotient `q ∈ [2, 10]` (both sampled uniformly)
- Dividend = `d × q ∈ [4, 100]`
- Result (correctAnswer) = `q`
- Prompt: `"${dividend} ÷ ${divisor} = ?"` using Unicode `÷` (U+00F7), NOT ASCII `/`

**Sampling strategy:** quotient-uniform via factor-uniform-then-compute, NOT dividend-uniform. Reasoning mirrors `multTo100`'s factor-uniform documentation: dividend-uniform would over-expose dividends with many divisor pairs (e.g. 12 = 2÷6, 3÷4, 4÷3, 6÷2 → 4 prompts) and under-expose those with few (4 = 2÷2 → 1 prompt). Factor-uniform gives every multiplication FACT and its inverse equal exposure — pedagogically what we want.

**Distractors:** 3 distinct integers from [2, 10] not equal to the correct quotient. The valid quotient range IS the valid distractor range; `pickDistractors` with `min: 2, max: 10` works directly (no `pickMultiplicationDistractors` adapter needed — division distractors are naturally "in-domain" by construction).

**Acceptance:**
- 1000 seeded samples: prompt parses `(\d+) ÷ (\d+) = \?`, divisor ∈ [2,10], dividend = divisor × quotient, quotient ∈ [2,10], correctAnswer matches quotient
- Choices length = 4, always include correct answer, no duplicates
- New `div-to-100` key visible in `config.scoring.mathDifficulty`
- `getImplementedIds()` includes `'div-to-100'`

### Story 3: `mixed` generator (Random from all implemented)

**Type:** Code (slightly more interesting — picks a delegate at draw time)

**Output:**
- `src/math/generators/mixed.ts`
- `src/math/generators/mixed.test.ts`
- New config entry `'mixed': 2.5` (single fixed multiplier representing the average difficulty; chosen between add-to-10's 1.0 and div-to-144's 4.0)
- Registry entry for `mixed`

**Math spec:**
- At each `generate(rng)` call, build the list of implemented MathIds EXCLUDING `'mixed'` itself (defensive — avoids infinite recursion if Mixed ever delegates to itself)
- Pick one uniformly using the injected rng
- Delegate to that generator's `generate(rng)` and return its Question verbatim
- The returned Question carries the delegate's prompt + answer + choices — Mixed doesn't transform anything

**Implementation note:** `mixed.generate` needs access to the registry. Cleanest approach: lazy `import('@/math/registry')` inside the function body to avoid a circular-import problem (registry imports mixed; mixed imports registry). Or split into a helper that takes the registry as a parameter. Will decide at implementation time based on what compiles cleanly.

**Acceptance:**
- 1000 seeded samples: each Question is a valid output from one of the 8 non-mixed generators (verified by parsing the prompt and checking against each generator's regex)
- Distribution across delegates is uniform within ±25% (each of 8 generators selected ~1/8 of the time across 8000 samples)
- `mixed` does NOT select itself (zero infinite-recursion risk)
- `getImplementedIds()` includes `'mixed'`
