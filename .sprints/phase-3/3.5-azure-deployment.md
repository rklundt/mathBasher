# Sprint 3.5: Azure Deployment

**Phase:** 3 (Backend + Accounts)
**Status:** Planned
**Blocks:** Public availability
**Depends on:** 0.7 (MVP shippable), and 3.1-3.4 if backend features are required at launch (otherwise can be done before phase 3 backend work)
**Estimated effort:** 1-2 days for first deploy; 0.5 day for later iterations

## Summary

Stand up the Azure resources, the CI/CD pipeline, and the operational essentials (custom domain, TLS, monitoring) needed to publish mathBasher to the public internet. Target architecture is a single-container Linux Azure App Service backed by Azure Container Registry, with CI/CD via GitHub Actions, secrets in Key Vault, and telemetry flowing into Application Insights.

This sprint can ship before any account/backend work — the MVP is fully playable without persisted high scores. Phase 3 then layers backend features onto this deployed app.

## Stories

### Story 1: Azure resources via Bicep (or Azure CLI script)

**Type:** Code
**Output:** `infra/main.bicep`, `infra/parameters.dev.bicepparam`, `infra/parameters.prod.bicepparam`, `infra/README.md`
**Acceptance:**
- Bicep template provisions, in a single resource group:
  - **Azure Container Registry (ACR)**, Basic SKU, admin disabled (managed-identity pull)
  - **App Service Plan** (Linux, B1 to start; can scale up later)
  - **App Service for Containers** (Linux, configured to pull from ACR via system-assigned managed identity)
  - **Application Insights** workspace + component, connection string surfaced as an output
  - **Key Vault**, RBAC-mode, with the App Service's managed identity granted "Key Vault Secrets User"
  - **Log Analytics workspace** (App Insights's required dependency)
- Parameters file pattern supports `dev` and `prod` environments with different SKUs/region/names
- `az deployment group create` with the parameters file is idempotent (re-run produces no diffs when nothing changed)
- `infra/README.md` documents the manual one-time bootstrap steps (subscription selection, RG creation, Bicep deploy command)

### Story 2: App Service configuration

**Type:** Code/data definition
**Output:** Settings applied via Bicep or a one-time `az` script; documented in `infra/README.md`
**Acceptance:**
- App Settings:
  - `WEBSITES_PORT = 8080` (tells App Service which port the container listens on)
  - `WEBSITES_ENABLE_APP_SERVICE_STORAGE = false` (we don't need the persistent volume mount)
  - `APPINSIGHTS_CONNECTION_STRING` = Key Vault reference to the secret stored in Story 3
  - `NODE_ENV = production`
  - `BUILD_HASH` = set by CI to the commit SHA
- Health check enabled on `/health` with 2-minute unhealthy threshold
- "Always On" enabled (prevents container unload on idle)
- HTTP/2 enabled
- HTTPS-only enabled
- Min TLS version: 1.2
- FTP/FTPS deployment disabled (we deploy via container only)
- One **deployment slot** named `staging` provisioned, with the same config as production except where overridden

### Story 3: Secret management

**Type:** Code/data definition
**Output:** `infra/README.md` updates; secrets stored in Key Vault
**Acceptance:**
- App Insights connection string stored as a Key Vault secret named `appinsights-connection-string`
- App Service's managed identity has `Key Vault Secrets User` role
- App Settings reference the secret with the syntax `@Microsoft.KeyVault(VaultName=<name>;SecretName=<name>)`
- No secrets in Bicep parameters files committed to git
- No secrets in environment variables in CI logs (use GitHub Actions secrets, masked)

### Story 4: GitHub Actions CI/CD pipeline

**Type:** Code
**Output:** `.github/workflows/ci.yml`, `.github/workflows/deploy.yml`
**Acceptance:**
- `ci.yml` runs on every push and PR:
  - Checkout, Node 20 setup, `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `docker build` (no push)
  - Required to pass before merge to `main`
- `deploy.yml` runs on push to `main`:
  - Builds the Docker image
  - Logs into ACR using a federated workload identity (OpenID Connect; no long-lived credentials in GitHub)
  - Pushes the image tagged `:${{ github.sha }}` and `:latest`
  - Deploys to the **staging** App Service slot
  - Runs a smoke test against the staging URL (curl `/health` for 200; curl `/` for 200 with HTML content type)
  - On smoke-test pass: swaps staging into production
  - On smoke-test fail: leaves production untouched, pipeline fails loudly
- Workflow files contain no secrets, no Claude/sprint references, no internal naming
- A README section in the repo (in `docs/deployment.md`) explains how to run a manual deploy if needed

### Story 5: Custom domain and TLS

**Type:** Code/data definition + human input (DNS)
**Output:** `infra/README.md` updates; domain wired
**Acceptance:**
- Custom domain (e.g. `mathbasher.example.com`) added to the App Service via Bicep or `az` script
- App Service Managed Certificate (free, auto-renewing) issued for the domain
- DNS records (CNAME + asuid TXT) documented for the human to set in their DNS provider — this is a manual step the sprint pauses for
- After DNS propagation, the site loads at the custom domain over HTTPS with a valid cert
- HTTP -> HTTPS redirect verified

### Story 6: Application Insights wiring

**Type:** Code
**Output:** Update `server/telemetry.ts`, `src/core/telemetry.ts`
**Acceptance:**
- Browser-side: `applicationinsights-web` SDK installed, initialized with the connection string read at runtime (via a tiny `/config.json` endpoint served by Express that returns only the public bits — connection string is OK to expose to the browser per Microsoft guidance, but routing it through the server keeps it from being baked into the Vite bundle)
- Server-side: `applicationinsights` (Node) SDK installed, auto-collection of console + HTTP enabled
- `cloudRoleName` properly set to `MathBasher.Web` and `MathBasher.Server` respectively
- `_th` helper now flushes events to App Insights when the connection string is present, falls back to console when not
- All sprint 0.x and 0.5+ events visible in App Insights Logs after a deploy

### Story 7: Smoke tests and observability dashboard

**Type:** Test + Code/data definition
**Output:** `docs/runbook.md`, an Application Insights workbook (exported JSON in `infra/observability/`)
**Acceptance:**
- `docs/runbook.md` documents:
  - How to view live logs (`az webapp log tail`)
  - How to query App Insights for round-completion events
  - How to roll back a bad deploy (slot swap reverse)
  - Common failure modes and what to check
- App Insights workbook visualizes:
  - Page loads per hour
  - Round completions per hour (correct vs failed)
  - Error rate
  - p50/p95 page load time
- Workbook JSON committed to repo so it can be re-imported into a new App Insights resource

### Story 7a: Build-output optimization — CDN cache headers for the Phaser chunk

**Type:** Code (App Service / CDN config)

**Context:** Carried over from sprint 2.2's six-reviewer audit (DevOps nice-to-have). The Phaser vendor-chunk SPLIT itself shipped early during sprint 2.2 — `vite.config.ts` now emits two hashed chunks: `phaser-<hash>.js` (~1.48 MB, changes only on Phaser upgrades) + `index-<hash>.js` (~110 KB, app code). What REMAINS for this sprint is the deploy-side half: the split only pays off if hashed assets get long-lived immutable cache headers so a returning user's browser actually reuses the cached `phaser-*.js`.

**Output:**
- Ensure the App Service / CDN config (Story 2) serves Vite's hashed `assets/*.js` + `assets/*.css` with `Cache-Control: public, max-age=31536000, immutable`.
- Ensure `index.html` itself is served `Cache-Control: no-cache` (it's the un-hashed entry point — must always re-fetch to pick up new asset hashes).
- Confirm in the deployment dry-run (Story 8) that a second page load reuses the cached Phaser chunk (DevTools Network → `phaser-*.js` shows "(disk cache)").

**Acceptance:**
- Hashed assets served with `Cache-Control: public, max-age=31536000, immutable`.
- `index.html` served `no-cache`.
- Dry-run confirms returning-visit reuses the cached Phaser chunk.

**Note:** the `manualChunks` split landed in sprint 2.2 (`vite.config.ts`) — `pnpm build` already emits the separate `phaser-*.js` / `index-*.js` chunks. This story is now cache-headers only.

## Notes for Claude Code

- This sprint requires Azure subscription access. The first time it's run, the human bootstraps: creates the subscription / RG, configures GitHub Actions federated identity with the subscription. Document those bootstrap steps clearly in `infra/README.md`.
- Prefer **federated workload identity** (OIDC) over service principal secrets for GitHub Actions -> Azure auth. No long-lived credentials in GitHub.
- App Service for Containers (Linux) is the chosen target. If the human ever asks about Container Apps, that's a different sprint — Container Apps is for microservices and KEDA scaling, neither of which mathBasher needs.
- The `infra/` folder, `docs/deployment.md`, and `docs/runbook.md` ARE committed (per `CLAUDE.md`'s "what is committed" rules). They contain no Claude or sprint references.
- The `.github/workflows/` files contain no Claude or sprint references. Workflow names use plain English ("CI", "Deploy to Production").
- If the smoke test gate is too strict for early iterations, soften it temporarily but never remove it — a deploy without a smoke gate WILL break production eventually.
- `WEBSITES_PORT = 8080` is App Service's contract; don't change the container's listen port without updating this setting in the same change.
- Container size: keep an eye on it. Each Phaser update can grow the bundle; if image creeps over 200MB, investigate before merging.
